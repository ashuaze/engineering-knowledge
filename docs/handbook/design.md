# 工程知识库设计蓝图

版本：v0.1 · 2026-10-16

## 1. 定位与名称

建议名称：**工程知识库 · Engineering Fieldnotes**。仓库名：`engineering-knowledge`。副标题：**从概念到生产系统的工程笔记**。

读者：软件开发、测试、运维与平台、数据、安全、架构及 AI 工程等方向的技术工程人员，以及正在建立工程基础的学习者。内容围绕计算机基础、软件系统、数据与生产工程展开，帮助读者理解机制、验证行为、分析故障并做出工程取舍。各篇正文与学习路径分别说明前置知识，支持按岗位、经验和任务选择入口。

当前 17 个领域均有正文入口，核心概念按[概念路线图](concept-roadmap.md)分批补充；优先解释原理、边界与关联，实践维度采用相应的实现示例与自检，独立实验后续推进。

长期重点积累底层原理、系统设计、故障诊断和技术权衡能力，核心资产包括可靠概念解释、可复现的实验、带边界的决策依据和经过订正的案例。第一阶段按一个维护者的写作与审阅能力控制规模。

## 2. 三个阅读入口，一份正文

| 入口 | 组织方式 | 用途 |
| --- | --- | --- |
| 知识地图 | 17 个稳定领域 | 查漏补缺、理解概念上下文 |
| 问题导航 | 症状或设计疑问 | 从实际工程困境进入 |
| 学习路径 | 目标、前置知识、练习、验收 | 有顺序地形成能力 |

术语索引提供关键词检索，文章目录提供当前内容列表。入口只是导航，同一篇正文始终放在其主要领域，其他入口链接到它。

默认学习顺序为：实际工程问题 → 定位关联概念 → 按需参考七维框架理解 → 实现或分析 → 测试与反例 → 记录设计取舍。领域与术语清单承担知识索引职责，学习进展由解释和工程证据体现。

示例：“请求重试导致重复创建”连接 API 幂等性、数据库唯一约束、Outbox 和 Agent 工具恢复。它们相互解释，但各自只维护一个核心问题。

## 3. 领域体系

| 层次 | 领域 |
| --- | --- |
| 基础 | 系统与操作系统、网络、数据结构与算法、语言与 Runtime |
| 应用 | 前端与浏览器、后端 API、软件架构、身份安全 |
| 数据 | 数据库、缓存与检索、消息事件、分布式系统 |
| 生产 | 性能容量、Linux 与交付、可观测性与可靠性、软件质量与研发 |
| AI | LLM、RAG、Agent、Memory、工具与评测 |

保留 17 个领域以承接原来的术语地图。领域首页说明范围、关键问题和术语；暂未写成正文的术语仍有简释。AI 初期放在一个大领域，只有当文章密度形成自然子主题时再增加导航，不提前迁移路径。

## 4. 七维学习框架与六种内容类型

Definition、Principles、Trade-offs、Implementation、Failure Modes、Practice、Related Concepts 提供定义、机制、取舍、实现、失败、验证和关联七个思考角度。文章按目的和内容选用维度，可合并、拆分、改名、调序或省略不适用项，不要求逐项展开。详细要求以[写作规范](editorial.md#concept-learning-template)为准。

| 类型 `kind` | 核心问题 | 组织重点（按内容调整） |
| --- | --- | --- |
| `concept` 概念 | 是什么，机制是什么？ | 围绕机制与边界，按需选用七维 |
| `comparison` 对比 | 两者在哪些维度不同？ | 共同问题、比较基准、机制差异、场景与取舍 |
| `pattern` 模式 | 如何反复解决一类约束？ | 问题约束、结构机制、故障窗口、成本与验证 |
| `case` 案例 | 怎样从证据定位问题？ | 案例来源、现象、假设、证据、处理、剩余不确定性 |
| `lab` 实验 | 如何亲手验证一个保证？ | 环境、命令、预期、不变量、故障注入、局限 |
| `decision` 决策 | 为什么在这个上下文选择它？ | 背景、约束、备选、决定、后果、重评条件 |

类型保存在文章元数据中；正文仍按主要领域存放。六类模板各自提供写作起点，章节名称、数量与顺序均可按内容调整；维度也可融入段落、图表或关联链接。现有七段式正文可继续使用。案例、实验和决策可以独立回答问题，也可与概念正文关联；同一实现或证据通过链接复用。质量检查关注问题是否得到解释、关键边界与证据是否充分，验证计划须明确标注。

建议概念约 800–1600 中文字；对比或模式约 1200–2200 字；长文按问题和章节拆分。这是编辑预算，不作为硬性质量指标。

## 5. 文件、标识与关联

正文路径采用 `docs/knowledge/<domain>/<slug>.md`，例如 `docs/knowledge/api/idempotency.md`。英文小写 slug，含义稳定，不放日期、编号或熟练度。

- 文章 `id`：如 `kb-api-idempotency`，一经引用保持稳定。
- 术语 `id`：如 `api.idempotency`，中英文别名保存在索引中。
- `prerequisites`：前置文章 ID；`related`：相关正文 ID。
- `tags`：控制在 2–5 个，描述横跨领域的主题，例如 reliability、concurrency、state。
- `summary`：一句话说明读者将解决的疑问。

首版校验 ID 唯一、领域、类型、状态、日期、关联对象和文件链接。后续可按 ID 生成反向链接；不必先引入数据库或图谱服务。

公开站点初期采用文件路由，保持领域和 slug 稳定。需要移动文章时保留原址兼容页，并把站内链接更新到新址；兼容页只指向新正文。最终域名确定后再生成 canonical URL 和 sitemap。

## 6. 三种状态分开管理

| 维度 | 值 | 含义 |
| --- | --- | --- |
| 术语覆盖 | 已收录 / 有正文 | 只有简释，还是已连接深入文章 |
| 内容成熟度 | evolving / reviewed / deprecated | 持续完善、完成审阅、已被替代 |
| 个人掌握 | L0–L4 | 陌生、能解释、能实现、能排障与取舍、能设计演进并传授 |

草稿放在不发布的 `drafts/`，通过校验并完成基本事实核查后移入 `docs/`，初始为 `evolving`。`reviewed` 要有可追踪审阅记录，不能只根据篇幅或生成时间自动授予。被替代的正文写明原因和替代入口。

P0/P1/P2 表示默认学习优先级，可按岗位、已有基础和当前任务调整；它不表示文章质量或个人熟练度。前端方向可优先浏览器与 Runtime，运维与平台方向可优先系统、交付与可靠性，数据与 AI 方向可优先相应领域。个人评估放在本地 `personal/`，避免混入公共知识。

## 7. 事实与验证

正文将来源事实、维护者分析、教学假设明确区分。标准或机制链接到 RFC、官方文档或原论文。涉及产品功能和版本时写出适用版本；更新主版本、出现勘误或案例反证时触发复查。

`updated` 表示正文修改日期；`last_verified` 表示最近完成文中声明范围核查的日期。格式调整不刷新核查日期。来源已核查不等于运行过代码，实验通过也不等于生产适用。

教学案例不使用未经测量的数字制造可信感；真实案例公开前移除客户、凭据和可识别信息。示例文章的“实验”与“教学推演”已经区分。

## 8. 发布产品形态

第一阶段：Markdown 仓库，首页说明定位，目录、索引、文章可在 GitHub 直接阅读，Issue 接收纠错。

第二阶段：VitePress 静态站，沿用 `docs/`，增加站内搜索、左侧领域导航、右侧目录、页脚来源与更新信息。顶部仅放“知识地图 / 问题 / 路径 / 文章 / 关于”。主页突出一个阅读起点和最近实质更新。

视觉方向：米白或白底、炭黑正文、低饱和蓝作为链接与选中态；正文约 72–80 字符行宽；大面积图表只用于解释机制。避免以装饰性大封面挤压阅读入口。

第三阶段：在出现明确读者需求后加入按标签筛选、反向链接、RSS 和系列专题。全文检索先使用静态站的本地搜索；需要更复杂检索时再评估额外服务。

## 9. 首批内容策略

保留宽知识地图，以“执行、重复、状态、失败”作为第一条深入主线。7 篇示例是：同步与阻塞、API 幂等性、Outbox、慢 API 排查、幂等性实验、可恢复 Agent Runtime、知识库 ADR。

前三篇建立概念和模式；实验将保证变成可运行断言；慢 API 案例示范证据推理；Runtime 文章连接 AI 专长；ADR 展示决策写法。全部以 `evolving` 起步。

后续首轮新增超时与重试预算、库存并发、对象级授权、浏览器长任务四篇，当时累计 11 篇正文。本地策略实验与待实测计划分别标记，持续选题与证据状态见[选题进度](topics.md)。

概念优先阶段的第一批再补系统、网络、算法、缓存、分布式、交付、测试七篇，当前共 18 篇正文；17 个领域均有所属正文，15 个领域有概念类入口。架构与性能的核心概念优先排入下一批；全量术语的深入解释仍持续分批积累。

## 10. 十二周积累节奏

下表保留为长期主题参考。当前执行顺序以概念路线图为准，独立实验单元在相应概念积累后安排。

默认每周一个写作单元；深文或实验可占两周。单元可是一篇短概念、一组订正或一个实验结果。维护占用约三成时间，优先修复读者会据此做错决策的问题。

以下周次为主题安排，具体产出进度以选题页与正文证据为准；已有机制文章的主题可继续补集成实验。

| 周次 | 主题与产出 | 验收 |
| --- | --- | --- |
| 1 | 审阅首批文章、确定署名和许可、准备首发 | 逐篇读完，命令通过，入口可用 |
| 2 | Event Loop 与任务调度 | 能解释 CPU 阻塞和 I/O 等待 |
| 3 | 超时、截止时间与重试预算 | 给出端到端预算和停止条件 |
| 4 | PostgreSQL 约束与隔离实验 | 复现一个并发异常并验证修正 |
| 5 | 缓存失效与热点回源 | 写出数据库故障下的降级边界 |
| 6 | Outbox relay 与消费去重 | 注入崩溃后可说明重复窗口 |
| 7 | 连接池、队列与尾延迟 | 用实际测量替换教学案例的假设 |
| 8 | SLI / SLO 与用户体验 | 定义计数口径及失败样本 |
| 9 | 租户授权与工具权限 | 越权用例被明确拒绝 |
| 10 | Agent Checkpoint 与恢复实验 | 工具结果未知时不盲目重放 |
| 11 | RAG 召回与回答评测 | 固定小数据集，区分两类失败 |
| 12 | 一篇系统设计串联及旧文订正 | 能从问题入口串联已有正文 |

## 11. 可持续维护

捕获问题 → 检索现有内容 → 确定一个问题 → 查一手资料 → 实验或反例 → 写作 → 校验与审阅 → 发布 → 收集订正。

每月集中处理失效链接、重复定义和术语合并；每季度重看学习路径是否仍能达成目标。以“读者能否解释底层原理、设计系统、诊断故障并说明取舍”和“旧文能否被修正”衡量质量。浏览量用于观察入口是否有效，术语数量和文章数量用于描述覆盖范围。

外部分发可将正文浓缩成公众号或 X 摘要，链接回稳定正文。原文发生实质更正时，更新变更记录，并对重要误导增加更正说明。

## 12. 首发标准

- 读者能从首页进入三类导航，且没有伪装成正文的占位页。
- 每篇正文有明确问题、边界、相关内容和来源或推演说明。
- 实验环境及可运行命令准确，失败路径有验证。
- 公共内容无私人记录、凭据和未经许可转载。
- 结构校验和索引检查通过，外部来源已人工抽查。
- 署名、内容与代码许可由维护者确定后加入正式 LICENSE。
- 部署网站时，再核对 base、移动端、搜索和页面链接。

当前交付已经建立 Markdown 内容骨架、索引、模板、示例、校验与实验。网站部署、域名、公开仓库和最终许可属于后续发布配置。
