# 写作与审阅规范

## 围绕一个可回答的问题

标题使用“对象 + 核心问题”或清楚的概念名。开头尽早说明工程问题、主要结论或观察及适用范围；展开顺序由文章目的与内容决定。避免连续堆砌缩写。

默认读者为不同方向的技术工程人员。文章说明必要的前置知识和适用场景；关键术语提供必要解释或索引入口，示例交代语言、平台与环境，便于其他方向的读者理解和迁移应用。

正文每次只拥有一个主要领域和一种类型。先搜索现有正文：能通过补充反例或章节解释的内容，优先修订已有文章。

## 七维学习框架：按内容选用

概念学习以实际工程问题为入口，领域与术语清单用于知识索引。长期重点积累底层原理、系统设计、故障诊断和技术权衡能力；用解释、实现、观测和决策证据记录进展。

七维提供思考与检查的角度。作者可按文章目的、问题范围和篇幅，选用、合并、拆分、改名、调整顺序或省略不适用的维度；维度可以融入段落、图表或关联链接，无需一一对应独立章节，也不要求每篇写满七项。现有七段式正文可继续使用，结构调整以改善解释与阅读为依据。

| 维度 | 内容 |
| --- | --- |
| Definition | 是什么？解决什么问题？ |
| Principles | 工作机制、核心原理 |
| Trade-offs | 优势、限制与适用边界 |
| Implementation | 实际代码或架构实现 |
| Failure Modes | 常见错误与故障模式 |
| Practice | 工程案例、测试与验证 |
| Related Concepts | 与哪些概念存在关联？ |

### 按文章类型组织

| 类型 | 推荐的组织重点 |
| --- | --- |
| `concept` 概念 | 可从七维出发，围绕需要解释的机制与边界选择结构；短文可合并相关维度 |
| `comparison` 对比 | 共同问题、比较基准、机制差异、场景与选择；按需用七维检查遗漏 |
| `pattern` 模式 | 问题与约束、结构与机制、故障窗口、成本和验证；按内容调整章节 |
| `case` 案例 | 现象、假设、证据、定位、处置与复盘 |
| `lab` 实验 | 目标、环境、步骤、预期、实际观察与局限 |
| `decision` 决策 | 背景、约束、备选、决定、后果与重评条件 |

上述顺序与 `templates/` 中的章节都是写作起点，可按实际内容调整。案例、实验和决策可以独立回答问题，也可作为其他文章的证据，通过链接复用。术语索引保留简释、别名与正文入口，无需展开七维。

选用的维度应有实质内容，重要前提与适用边界不能因结构精简而遗漏。涉及实现时，可使用代码、架构流程或现有实现链接，交代环境与验证状态；涉及实践时，区分已执行结果、验证计划和教学推演，并说明证据范围。相关概念按需要解释前置、对比、组合或替代关系，正文关联与元数据保持一致。

概念优先阶段按[概念路线图](concept-roadmap.md)分批补充。说明性实现、纸面推演、反例与自检按内容需要选用；不适用的维度可以省略，不必留下空标题或编造案例。来源核查、理论推导与代码执行分别记录。

## 元数据

六种模板的字段通用。为了免除维护脚本的第三方依赖，当前约定为平铺 YAML，字段值使用 JSON 标量或数组；不要使用多行、嵌套 YAML 或 YAML 未加引号日期。此格式仍是合法 YAML。

| 字段 | 规则 |
| --- | --- |
| id | `kb-` 开头，稳定且全库唯一 |
| title / summary | 面向读者，不以内部任务名命名 |
| kind | concept、comparison、pattern、case、lab、decision |
| domain | `data/domains.json` 中一个领域 ID |
| status | evolving、reviewed、deprecated |
| created / updated | ISO 日期，created 不晚于 updated |
| last_verified | 有核查时填 ISO 日期；未核查用 null |
| verification | source-checked、tested、design-proposal 三选一 |
| prerequisites / related | 正文 id 数组，不能指向自身或不存在文章 |
| tags | 小写主题标签，建议 2–5 个 |

`source-checked` 仅表示核查了来源支持的机制；`tested` 表示对应实验执行通过；`design-proposal` 明示设计建议或教学推演，不填 last_verified。需要记录更细证据时在正文“验证记录”中写明范围与环境。

## 来源、图表和代码

优先官方文档、标准和原论文。关键结论附近或对应章节说明来源，文末列资料入口和核查日期。对参考资料进行自己的综合分析，保留引用范围，避免大段转载。

图说明一个关系；涉及并发、故障窗口时画状态或时序。首版内容使用 Markdown 表格与代码块，便于 GitHub 阅读；引入 Mermaid 时要同时验证 GitHub 和站点的渲染。

可运行代码放 `examples/`，文章写运行环境和结果。说明性伪代码明确标注；未经执行的代码不写“验证通过”。教学数据和模拟案例必须显式标记。

## 成熟度与审阅证据

`evolving`：已经能回答问题，有边界、来源或推演说明，可对外阅读。

`reviewed`：除上述条件外，由维护者或同行完成实质核对；在正文记录审阅者角色、日期、范围、关联 Issue/PR。当前首批正文尚未获得此状态。

`deprecated`：保留历史上下文，在开头写明替代文章及弃用原因。

## 更新策略

按变化触发复核：依赖主版本变化、标准修订、来源失效、读者提出反例。AI 工具协议和框架文章建议每 1–3 个月抽查；稳定原理可每年抽查。到期只意味着应排入复核，不直接判定内容错误。

## 发布前检查

1. 读者问题与范围明确，相关定义、证据与推理能相互支持。
2. 涉及方案或保证时，说明成立条件、适用边界和关键失败风险。
3. 区分来源事实、个人建议、教学假设与实测结果。
4. 按文章目的提供必要的案例、验证方法、自检或概念关联，更新相关导航。
5. 检查保密信息、链接、标识和适用版本。
6. 运行仓库校验、索引一致性和受本次变更影响的实验。

人工审阅检查所选结构能否回答问题、关键内容是否遗漏，以及结论与证据是否相称。自动校验检查元数据、关联与内部链接，不以章节名称、数量或顺序判定文章是否完整。

## 个人能力评估

L0 陌生；L1 能用自己的话解释；L2 能实现并验证；L3 能排障、比较和做取舍；L4 能设计演进并教会他人。附证据路径或复盘，比只填等级有用。此评估保存在 `personal/`，不进入公开站点。
