# 慢 API 排查：把执行时间与排队时间分开

## 案例来源与限制

这是**教学推演**，不是作者真实生产事故；不提供虚构的实测延迟、QPS 或优化收益。目标是展示一种可用于真实案例的证据组织方式。

假定现象：某个 API 在业务高峰变慢，CPU 利用率看起来不高，数据库单条查询也不明显变慢。以上是问题设定，尚未证明瓶颈位置。

## 先定义时间边界

把用户等待拆成入口排队、应用调度、连接获取、数据库执行、外部调用和响应传输。各阶段可能存在重叠，不能把所有 span 的耗时直接求和；先确认链路是否顺序执行以及追踪是否完整。

## 假设与反证

| 假设 | 应寻找的证据 | 什么会削弱该假设 |
| --- | --- | --- |
| 连接池等待 | 连接获取耗时、活跃连接、等待队列 | 获取连接耗时稳定且很短 |
| 事件循环被占用 | 事件循环延迟、CPU profile、同步调用 | 延迟与慢请求无时间关联 |
| 数据库锁等待 | 阻塞链、事务年龄、等待事件 | 慢窗口中没有对应等待 |
| 下游变慢或重试放大 | 依赖 span、重试次数、超时分布 | 下游耗时和请求放大均无变化 |
| 应用前已经排队 | 网关接收和应用接收时间差 | 请求进入应用前无等待 |

此处的观测项目是排查建议，不是对当前假设的证明。

## 若证据指向连接池

进一步检查连接持有时间，长事务、游标未关闭、事务内外部 HTTP 调用都可能延长占用。连接池满也可能只是下游变慢的症状。直接把池从小值放大，可能将更多工作压到数据库并加重等待。

候选措施包括缩短事务范围、为等待设定超时、限制应用并发、修复资源泄漏。是否增加连接数，需要数据库剩余容量和压测证据支持。

## 验证方案

固定工作负载、数据规模和依赖条件，对照修改前后：端到端延迟分布、连接等待、连接占用、吞吐、错误率和数据库资源。既检查正常高峰，也检查下游退化时是否出现更长队列。

这里只提出验证方法，没有报告“优化成功”。完成实际实验后，保留原始结果及环境，再将本文扩展成实测案例。

## 自检与关联

当看到“SQL 很快，但 API 很慢”，能否指出至少三个 SQL 执行之外的等待位置？如果证据推翻第一个假设，下一步收集什么？

- [超时与重试预算](../reliability/timeouts-and-retry-budgets.md)：检查排队、单次超时和多层重试如何消耗总时间。
