# 事故响应与复盘：告警恢复了，为什么还不能结束处理

学习入口：错误率回落后，积压订单还没处理完，可以宣布事故结束吗？前置：[服务目标](slis-slos-and-error-budgets.md)、[遥测信号](logs-metrics-and-traces.md)。本文建立响应和学习的概念；时间线、角色分配及行动项都是纸面设计，没有处置真实事故、发送通知或执行恢复演练。

定位时连接服务与资源的观察见[RED与USE](red-use-service-signals-and-resource-evidence.md)；主动验证故障及停止/恢复职责见[混沌工程与受控故障](chaos-engineering-hypotheses-stop-conditions-and-recovery.md)，不把演练计划当作事故结果。

## 告警触发、事故声明与用户影响各有证据

告警是对某种条件的检测结果，事故则是需要协调响应的异常情境。一个事故可能产生很多告警，也可能先由用户报告而没有触发任何告警。告警规则恢复只表明对应条件当前不再满足，不能直接推出所有用户路径、积压和数据都已恢复。

响应先明确已知影响、证据时间、涉及范围及未知项；严重程度和升级条件由服务和组织预先约定，不存在适合所有团队的统一分级数字。影响扩大、跨团队依赖或单人无法同时处置和沟通时，应按约定尽早组织协调，不需要等到查明原因才声明事故。

例如订单写入成功但确认消息丢失，接口错误率不一定明显上升，用户却可能重复下单。此时“HTTP 都是成功响应”只覆盖接口层；业务正确性与消息处理仍需检查。[SLI/SLO](slis-slos-and-error-budgets.md)帮助定义观察对象，但不能代替事故中的影响确认。

## 协调要让动作、责任与当前状态可见

[Google SRE 的事故管理](https://sre.google/sre-book/managing-incidents/)介绍指挥、操作、沟通和计划分工，并强调实时状态文档与明确交接。团队可以按规模合并角色，关键是工作有人承接且不会互相覆盖。

| 责任 | 需要保持清楚的内容 | 常见失效 |
| --- | --- | --- |
| 响应协调 | 当前目标、优先级、分工、升级与交接 | 所有人都深入单个技术问题，没人看总体影响 |
| 处置操作 | 谁在改什么、依据、预期效果和停止条件 | 多人同时修改同一系统，无法判断因果 |
| 沟通记录 | 已知影响、已做动作、未知项、下次更新点 | 把猜测当作确认原因或承诺未经验证的恢复时间 |
| 后续安排 | 替班、依赖团队、临时措施及遗留风险 | 交接后丢失状态，临时配置永久遗留 |

指挥并不意味着所有动作都由一个人亲自批准到细节，也不表示排查专家可脱离共同状态擅自改动。应明确可自主执行的范围、会互相冲突的变更以及需要升级的动作。只读调查和有副作用的操作也要区分，避免“只是看看”实际触发负载或重启。

实时文档以当前影响、负责人、操作记录和下一步为核心，不必等到排版完整。交接需要新负责人确认接手，并同步当前假设、已排除项、进行中的动作、访问限制和下一次沟通；把文档链接发出去并不证明对方已承担责任。

## 止损、修复与恢复验收解决不同问题

止损先限制当前损害，例如暂停不安全写入、关闭有问题的路径或把流量转移到已验证容量。它可以在根因尚未确定时进行，但仍需比较动作本身的风险及观察效果。不能因“回滚通常最快”就忽略数据库迁移、旧版本兼容或剩余区域过载，见[交付与回滚](../devops/build-deploy-rollback.md)。

修复针对导致问题的机制；恢复验收则确认服务和业务重新满足约定。一个临时配置可能已经止住错误，但仍需补处理积压、核对外部动作和修复数据。应规定观察窗口、抽查/对账范围及遗留事项责任，不能只等一张指标图变绿。

下面是假设全部时钟一致、影响起止可以确认的教学时间线，所有时刻均为同日 UTC+8：

| 时刻 | 纸面事件 | 可以说明什么 |
| --- | --- | --- |
| 14:00 | 第一批订单确认受影响 | 本例影响起点 |
| 14:03 | 告警触发 | 检测比影响起点晚 3 分钟 |
| 14:05 | 声明事故并明确分工 | 协调开始，尚未止损 |
| 14:12 | 关闭问题路径，新订单恢复 | 本例止损耗时为自影响起点起 12 分钟 |
| 14:20 | 积压处理及订单/外部结果核对满足验收 | 本例业务恢复耗时为 20 分钟 |
| 14:30 | 完成观察，结束集中响应并交接后续项 | 响应结束，与恢复时刻不同 |

本例从影响起点至响应结束为 30 分钟，从声明事故至响应结束为 25 分钟；两种口径应分别说明。14:12 的状态不能抹掉此前订单的影响。若只能从日志推定 14:00，则应记录置信范围，而非给出虚假的精确起点。报告指标时注明起止事件与样本；单次事故不能叫作“平均恢复时间”，不同起止口径也不能直接比较。[恢复目标](failure-domains-redundancy-and-recovery.md)进一步区分目标值和观察值。

## 复盘解释促成条件，行动项需要验收

[Google SRE 的复盘实践](https://sre.google/sre-book/postmortem-culture/)强调以事实和促成因素学习，避免把分析终止在个人失误。无责复盘仍应准确记录动作与后果，也要为改进明确负责人；它不意味着删除责任信息或不跟踪完成情况。

对纸面订单事故，“有人开错开关”只描述一个触发动作。还可以追查：为什么该配置组合被允许、开放前检查为何未覆盖、谁能看到实际生效版本、为何告警晚于用户影响、恢复时为何需要手动对账。应把确认事实、合理假设和仍待验证部分分开，保留日志/追踪与变更记录来源。复杂事故未必有一个能解释全部损害的单一原因。

| 行动项示例 | 交付验收 | 效果验证 |
| --- | --- | --- |
| 限制不兼容配置组合 | 指定维护人/期限，检查能拒绝已知非法组合 | 后续演练或观察确认限制未被其他入口绕过 |
| 增加业务确认[延迟](../../glossary/performance.md#performance.latency-throughput)信号 | 指定负责人、阈值依据和告警路由 | 用受控情境确认可及时发现且能抵达值班人 |
| 完善积压恢复办法 | 记录重复处理、对账与中止条件 | 在约定边界演练并核对结果与恢复耗时 |

这些是待实现的行动设计。代码合入、文档写完和告警创建是交付证据，是否减少风险还需相应验证；效果暂时无法确认时，保留该限制并安排复查。复盘发布范围也应考虑敏感数据和访问权限，协作不要求公开凭据或用户原始内容。

## 自检与关联阅读

自检：为什么 14:12 不能直接宣告业务恢复？因为旧订单的积压和外部结果尚未通过验收。为什么“提醒操作人小心”不够？它没有说明系统怎样阻止或减轻同类条件。为什么需要交接确认？因为可访问文档与有人负责下一步是不同状态。

- [日志、指标与链路](logs-metrics-and-traces.md)：采样和传播会限制可观察证据。
- [故障域与恢复目标](failure-domains-redundancy-and-recovery.md)：共同故障、恢复顺序和 [RTO](../../glossary/reliability.md#reliability.recovery)/RPO。
- [主干开发与功能开关](../engineering/trunk-based-development-and-feature-flags.md)：配置变更与路径回退的边界。
- [IaC 与状态漂移](../devops/iac-state-drift-and-change-plans.md)：应急变更之后，如何协调声明和实际资源。
