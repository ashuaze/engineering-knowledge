# 设计文档与决策记录：方案获批，为什么仍不等于已经交付

学习入口：仓库里有一份 accepted 的决定，为什么没人能回答实现到了哪一步、实际行为是否符合预期？讨论、决定、实现和验证各有自己的状态，需要建立可追溯关系。

前置：[质量属性与架构决策](../architecture/quality-attribute-scenarios-tradeoffs-and-adrs.md)。本文聚焦文档协作和生命周期，不重复完整架构评估；例子为纸面流程，没有批准任何真实方案或改变现有知识库 [ADR](../../glossary/engineering.md#engineering.design-docs) 的证据状态。

## 三类文档服务于不同问题

| 文档 | 主要用途 | 应连接的内容 |
| --- | --- | --- |
| Design Doc | 解释问题、目标及候选设计 | 上下文、范围、取舍与验证安排 |
| 工程 RFC | 为尚未确定的重要变化征求意见 | 讨论范围、待答问题、决定方式 |
| ADR | 保留某个重要决定及其后果 | 原因、备选、状态与后续替代关系 |

一个项目可以合并载体，但不能因此抹掉问题的区别。这里的 RFC 指工程协作用法，与 IETF 的文档系列按上下文区分；团队的状态名和审批规则也不必相同。

[Malte Ubl 的 Design Docs at Google](https://www.industrialempathy.com/posts/design-docs-at-google/)强调背景、目标/非目标、设计和取舍，并说明格式应服务于问题。非目标是合理但本次明确不承担的能力，不是把“不得泄露数据”这类基本约束随意排除。

## 让讨论收敛到明确的决定对象

教学提案是把导出任务改为异步操作。文档需说明原先哪里阻塞、谁受影响、何时算完成、为何采用任务资源，以及继续同步或限制规模等备选的代价。

“支持异步”还不足以实施，应明确任务身份、查询权限、取消含义、结果保留、兼容与迁移。无法确定的吞吐或失败行为，标为假设并连接验证计划，不能把估算写成已经测得的事实。

[Rust RFC 流程](https://rust-lang.github.io/rfcs/)展示如何讨论重大变化，也明确 active 不代表已经有人负责实现或获得实现优先级。这是特定项目的流程例子，不是所有仓库必须照搬的审批制度。

## 决定状态与交付证据并行维护

| 教学状态 | 能说明什么 | 还需什么 |
| --- | --- | --- |
| 提议中 | 存在待讨论方案 | 关键问题、约束与相关方意见 |
| 已接受 | 在当时条件下选择了方案 | 实现任务、负责人及验证安排 |
| 已实现 | 指定版本已有相应代码/配置 | 真实依赖、部署及业务验收 |
| 已验证 | 声明场景有相应证据 | 证据日期、环境及剩余范围 |

这里是四种不同问题的教学组织方式，不是统一状态机。“已验证”也必须带范围；某次本地测试通过不能自动变成所有环境均已验证。

## 保留历史，同时提供当前入口

[Nygard 的 ADR 方法](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)保留被替代决定。后续条件变化时，新记录说明为什么重评、替代了什么，以及旧理由哪些仍成立；不把旧文静默改成仿佛一直采用新设计。

另一方面，读者需要能找到当前有效约束。可以维护状态和相互链接，将历史决定与当前接口/运行说明连接起来；“保留历史”不等于要求新人猜哪份才有效。

## 文档更新也有边界与成本

影响外部契约、数据归属或故障恢复的变化应连同设计理由更新；变量重命名未必需要新提案。选择足以表达风险的最小文档单元，避免用页数和审批人数衡量质量。

复核时把事实、假设、决定和证据分别标明；检查读者是否能找到实施范围、停止/回退条件及遗留责任。设计清楚能帮助协作，但不能替代评审、实现和实际验证。

## 自检

1. Design Doc、工程 RFC 和 ADR 各自主要回答什么？
2. 异步导出为什么不能只写“改为后台执行”？
3. accepted/active 为什么不能证明实现已交付？
4. 旧决定被替代后，为什么同时需要历史和当前有效入口？
5. 什么变化值得更新决定记录？应怎样区分事实、假设和证据？
