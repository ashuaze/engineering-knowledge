# 规格驱动与验收追溯：文档完整，为什么仍可能实现了错误目标

学习入口：按照一份规格实现并通过全部样例，为什么用户仍无法完成任务？需要同时检查规格是否表达了正确目标，以及实现是否满足规格声明的行为。

前置：[测试范围](test-scopes-and-doubles.md)、[API 契约](../api/contracts-and-pagination.md)。本文把“[规格驱动开发](../../glossary/engineering.md#engineering.sdd)”用作以可检查约束组织实施的工作方式；不假定它有唯一通用流程、工具或文件布局，也不等同于某种代码生成方法。支付例子为纸面设计，没有实现或执行验证。

## 先区分需求目的、规格与设计

需求目的解释谁为何需要什么能力；规格约束可观察行为和允许范围；设计选择如何满足这些约束。三者可以相互影响，但“采用某个框架”本身不能代替用户结果。

规格可以包含自然语言、状态关系、接口约定和例子。可执行例子便于持续检查；形式化模型可以表达更严格的性质。使用其中一种表达，并不自动意味着完整需求、全部运行条件或模型与真实实现都已被证明。

[NASA 的需求管理说明](https://www.nasa.gov/reference/6-2-requirements-management/)强调来源、双向追溯和变更影响。本文借鉴这些方法，不把航天项目的具体组织制度推广为所有软件项目要求，也不声称符合 NASA 的过程要求。

## 将模糊承诺改成可观察的契约

教学目标：“付款页面等待结束后，用户可以确认付款结果，重复操作不能产生未经允许的重复扣款。”需要继续澄清：

| 要素 | 本例需要写清的内容 |
| --- | --- |
| 主体与输入 | 谁能创建/查询付款，金额单位、取值及操作身份 |
| 前置条件 | 订单状态、权限和参数一致性要求 |
| 正常结果 | 何时代表接纳，何时代表业务成功，怎样查询 |
| 不确定结果 | 响应丢失或等待到期后返回什么、沿用何种身份恢复 |
| 生命周期 | 查询结果和去重信息保留多久，到期后怎样处理 |
| 失败边界 | 外部渠道重复、并发提交、取消和人工修复的职责 |

不能只规定 HTTP 返回结构，却不说明付款是否已发生。服务端超时也不能自动保证外部扣款撤销；若需要某种保证，必须说明实现边界、外部协议和可检查证据。

## 追溯不是只给表格打勾

可以给关键要求分配稳定标识，例如 `PAY-03` 表示响应不确定时按原操作身份查询。把它连到设计决定、实现位置、测试/检查方式和本次结果；反向也能说明某个检查针对哪条要求。

“有链接”仅证明记录了关联。应核对检查是否真的观察了要求中的结果、是否用了正确环境，以及未运行、失败、例外和待补项是否被明确保留。十条要求各有链接，不等于十条均已满足。

## 验证符合规格，还要确认规格服务于目标

[NASA SWE-055](https://swehb.nasa.gov/spaces/SWEHBVD/pages/102695440/SWE-055%2B-%2BRequirements%2BValidation)讨论需求在客户环境中满足预期的问题。术语在不同过程里可能更细；这里明确区分两个问题：实现是否符合声明，声明是否适合真实使用目标。

例如规格允许不确定付款永久显示“失败”，实现完全照做仍可能诱导用户发起第二次付款。应与相关方确认不确定状态、查询和恢复体验，再检查真实渠道效果，而不是只调整一个断言让报告变绿。

[Cucumber 的可执行规格说明](https://cucumber.io/docs/)说明例子如何连接自动化代码。例子不能穷举所有输入；还需用边界、性质、状态序列、真实协议与必要的人工检查补充，且说明每项证据范围。

## 规格变化要评估已有实现和历史状态

把结果保留期从 24 小时改为 7 天，会影响存储、权限撤销、旧客户端和去重时限；修改文字不是完成迁移。保留版本、理由与兼容安排，并找出需要更新或重新执行的验证。

基线表示在某个时间点被约定的版本，不意味着永远冻结需求。若发现规格矛盾或目标改变，应公开处理决定和影响，避免代码、文档与验收各自代表不同版本。

## 自检

1. 需求目的、规格和实现设计分别约束什么？
2. 付款“返回超时”为什么不能直接规定成“没有扣款”？
3. 要求都有测试链接，为什么仍不能宣布全部满足？
4. 实现符合规格，与规格适合客户目标，有什么区别？
5. 延长结果保留期时，除了修改文档还要检查哪些影响？
