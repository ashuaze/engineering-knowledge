# 测试稳定性与隔离：单独通过，为什么组合运行却失败

学习入口：同一提交第一次失败、第二次通过，是否可以直接合并？前置：[测试范围与替身](test-scopes-and-doubles.md)。本文讨论测试结果为何不稳定，以及怎样保留足以追查的证据；例子是纸面设计，没有运行 pytest、Playwright 测试套件或测量失败率。

怎样组合稳定而有用的检查见[测试金字塔与证据组合](test-pyramids-risk-portfolios-and-coverage.md)；等待、诊断及维护成本如何进入开发任务见[黄金路径与开发者体验](golden-paths-developer-experience-and-platform-feedback.md)。

## 间歇失败描述现象，还没有确定责任

[Flaky Test](../../glossary/engineering.md#engineering.flaky-tests) 指看似相同条件下时而通过、时而失败的测试。这里的“相同”常常只记录了提交，实际的时间、调度、输入、依赖和遗留状态却不同。失败可能来自测试安排，也可能暴露产品竞态、外部服务波动或执行环境故障，不能先把它归类为“测试自己坏了”。[pytest 的说明](https://docs.pytest.org/en/stable/explanation/flaky.html)将未控制状态、过严断言和[线程](../../glossary/systems.md#systems.execution-units)安全列为常见调查方向。

可重复失败也可能是在稳定地检查错误要求；稳定通过同样不能证明要求完整。测试稳定性解决的是反馈能否被理解和复查，要求是否正确、覆盖是否充分还需分别判断。

## 隔离必须说明共享资源在哪里

假设 A 测试把进程内默认时区从 UTC 改为东八区，结束时没有恢复；B 测试用默认时区解析同一日期，期望 UTC 结果。B 单独运行通过，A→B 则失败。直接给 B 增加[重试](#重试和临时隔离都要留下失败身份)，若重试仍在同一进程，它可能继续失败；换新进程后通过，则可能只是清除了泄漏条件。

新进程重试通过仍不能证明进程内残留就是原因，因为时间、调度或外部响应也可能同时改变。这个纸面例子已知的依赖是“前一个测试留下的默认设置”。让 B 显式注入所需时区、缩小 A 的修改范围并恢复原值，可以去掉该隐含依赖。把所有测试固定为 B→A 只是在回避触发顺序。若业务本来要求多个操作组成一个流程，则应把流程及其初始状态定义为一个检查单元，不能假装每一步都独立。

| 边界 | 常见残留或冲突 | 可以核对的隔离安排 |
| --- | --- | --- |
| 单次测试对象 | 可变对象、替身调用记录、缓存 | 每次创建实例，明确初始化和释放 |
| 进程 | 全局变量、环境变量、默认时区、后台线程 | 显式依赖、恢复上下文，必要时独立进程 |
| 浏览器上下文 | [Cookie](../../glossary/security.md#security.sessions)、本地存储、登录状态 | 独立上下文及各自页面 |
| 外部系统 | 同一账户、数据库记录、待处理消息、文件目录 | 独立数据身份、限定访问范围、可靠回收 |

[Playwright 的隔离模型](https://playwright.dev/docs/browser-contexts)为各测试提供独立浏览器上下文；这不自动分离服务端的同一账户或数据库。两个上下文同时改一张共享订单，仍可能互相干扰。隔离策略应沿着真正的共享资源检查，不能只凭“每个测试都有新页面”推断全部独立。

清理应覆盖失败路径，并等待自己启动的任务结束；进程被强制终止时，普通清理钩子未必执行。外部数据还需可识别的归属和兜底回收，清理范围不能碰到别的测试。提高隔离程度有成本，也可能藏住必须验证的真实竞争；验证[并发](../../glossary/systems.md#systems.concurrency)行为时，应在单个场景里主动组织竞争并检查[不变量](../../glossary/systems.md#systems.atomicity)，而不是依赖两个无关用例偶然撞车。

## 控制输入与等待条件，保留真实约束

随机种子可帮助重放生成的数据，但没有固定外部响应、任务顺序或时钟。记录种子时还需记录实际失败输入及生成器/依赖版本；不能仅凭一个种子承诺跨版本、跨调度完全重放。[属性测试与状态模型](property-testing-and-state-models.md)进一步解释输入缩减与状态序列。

对于异步操作，固定等待一小段时间把“应该完成”误当作“已经完成”。更明确的设计是等待可观测条件，并设置总[截止时间](../../glossary/reliability.md#reliability.retry-budget)、记录未满足的条件。等待不能改变业务要求：若契约要求重复提交只生成一份结果，轮询到某一刻看见一份记录，不足以证明稍后不会再生成第二份。还需定义观察窗口或终止条件及对副作用的检查范围。

真实的时效要求也不能通过无限延长等待期限消掉。可以将业务时间作为可控依赖用于逻辑检查，再保留少量真实时钟/调度的集成检查；两者的证据不同。容差要来自数值或时间契约，而非为了让失败消失而放宽断言。

## 重试和临时隔离都要留下失败身份

重试增加一次观察机会，不解释首轮为何失败。[Playwright 的重试文档](https://playwright.dev/docs/test-retries)区分首次通过、失败后重试通过和全部失败；失败后会替换工作进程，相应初始化也可能重跑。因此不同尝试不仅时间不同，还可能换了执行状态；远端遗留数据仍需自己处理。

一条可追查记录至少包括：源码/制品版本、配置与依赖、测试及尝试编号、顺序和并行度、输入/种子、资源身份、实际断言结果及适量日志或追踪。敏感凭据应脱敏。首轮失败不能被最后一次绿色状态覆盖；若重试会重复付款、发信或写入，重复执行本身也需要隔离或明确的[幂等](../../glossary/api.md#api.idempotency)安排。

临时移出阻断集合可以降低反馈干扰，但必须公开显示尚未提供的覆盖，指定维护人、修复条件和到期复查，必要时用其他检查保护高风险行为。移除阻断与修复是两种状态；关闭测试后“全绿”不能当作风险已经消失。

## 修复证据应能区分原因与偶然通过

对前面的时区例子，可先记录 A→B 能触发的条件，再确认修复后 B 独立、A→B、B→A 都满足各自要求，并检查原有行为没有被删去。对于共享账户冲突，还需有针对性的并行安排；只证明串行通过，不能推到并行安全。

反复运行未再失败是有用观察，但有限次数内的零失败不证明失败概率为零。环境故障、产品竞态和断言错误应有各自的修复依据。复盘时关注失败是否可解释、首轮证据是否保留、反馈耗时和被隔离的覆盖，不能仅用最终通过率评价质量。

自检：新进程重试通过能排除服务端残留吗？不能。固定种子能排除并发竞态吗？不能。把 B 放到 A 前面能证明隔离吗？不能；它只改变了当前执行顺序。
