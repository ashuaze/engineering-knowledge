# CRDT：怎样合并并发更新，收敛又没有保证什么

学习入口：两个失联副本都允许修改购物车，恢复通信后怎样保留双方的操作？“取较大值”“把集合并起来”有时看起来正确，却可能丢计数或复活已删除项目。[CRDT](../../glossary/distributed.md#distributed.crdt) 把允许的更新与并发合并语义一起设计，在传播和故障前提成立时保证副本收敛；用户想要的业务约束仍需单独检查。

前置：[一致性与复制](consistency-and-replication.md)、[因果与向量时钟](logical-clocks-causality-and-concurrency.md)。本文讨论同一逻辑对象的受信副本、有效操作和最终能传递更新的模型。向量、集合、状态表和库存反例均为纸面推演，不是可直接投产的同步实现。

## 先规定并发结果，再讨论怎样发送

Conflict-free Replicated Data Type（CRDT）是为复制与无协调本地更新设计的数据类型。两个副本纳入相同更新后，应按约定语义得到相同状态；这不要求每一刻都读到全局最新值。持续分区或永久丢失尚未传播的唯一副本，不能凭数据类型名称获得最终交付。

[Preguiça、Baquero、Shapiro 的 2018 年综述](https://arxiv.org/pdf/1805.06358)区分并发语义与同步模型。例如同一元素的 add 与 remove 并发，到底保留、删除还是展示冲突，需要先选契约。CRDT 可以提供不同答案，“没有需要人工处理的复制分歧”不表示业务不存在冲突，也不表示所有类型都保留相同意图。

两个常见传播方向各有条件：

| 方式 | 传播与合并 | 不能省略的前提 |
| --- | --- | --- |
| 状态型 | 发送累积状态，按约定 join 合并 | 合法状态形成相应偏序；本地更新向上增长；合并为最小上界；传播最终覆盖更新 |
| 操作型 | 传播在源副本生成的操作效果 | 可靠交付，以及设计要求的去重/因果顺序；常见模型要求并发效果可交换 |

交换律使到达次序不影响结果，结合律使分组合并不影响结果，幂等性使同一状态重复合并没有额外效果。状态型的这些性质不能直接推广为“操作消息可以重复执行”；普通 `+1` 执行两次仍加二。操作型实现必须明确一次应用、去重或操作自身幂等的责任，不能只因操作可交换就忽略重复。

## 计数器为什么合并分量，而不是合并总数

固定副本身份为 A、B，初始向量 `(0,0)`。G-Counter 的教学规则是：A 只增加 A 分量，B 只增加 B 分量；读取为各分量之和；状态合并逐分量取最大值。

| 阶段 | A 状态 | B 状态 | 对应读数 |
| --- | --- | --- | --- |
| 断联前 | `(0,0)` | `(0,0)` | 都为 0 |
| A 增加 3，B 独立增加 4 | `(3,0)` | `(0,4)` | A 见 3，B 见 4 |
| 两侧交换状态 | `(3,4)` | `(3,4)` | 都为 7 |
| 再收到旧 `(3,0)` 或重复 `(0,4)` | `(3,4)` | `(3,4)` | 仍为 7 |

若只保存总数并取 max，会得到 4，漏掉 A 的 3；直接相加两个汇总则会在重复同步时变成 14。逐分量 max 区分了每位写者的累积贡献，既保留并发增加，又避免旧状态重复计费。

这个例子的偏序是逐分量 ≤，join 为逐分量 max。任意本地更新不减少分量，max 不丢已知贡献，且满足上面三条合并性质。两侧最终收到包含相同贡献的状态，就得到相同向量。这里的“向上增长”指内部状态的偏序，不能简单理解为所有用户可见值必须递增。

身份与恢复也属于算法前提。若 A、B 共用一个分量并各自从 0 加 1，合并只能留下 1；若 A 重启后把分量从 3 清零再加到 1，旧 3 又会覆盖它。需要保留身份与累积状态，或使用不会混淆旧贡献的新 incarnation 及相应合并协议，不能随意回收分量。该向量是计数器贡献状态，不自动等同完整的逐事件[向量时钟](../../glossary/distributed.md#distributed.vector-clocks)。

## 可减计数器仍可能违反余额约束

PN-Counter 用两个只增的贡献向量 P、N，读数为 `sum(P)-sum(N)`；增加更新 P，减少更新 N，两个向量各自逐分量 max。可见值因减少而下降，内部两个分量集合仍向上增长。

设初始总额 1 已作为唯一初始贡献纳入 P。A、B 都看到余额 1，各自在本地检查后减少 1，N 最终合并出两个减少，结果为 `1-2=-1`。副本完全可以正确收敛到 -1，同时违反“余额不得为负”。

若必须保护有限库存，需要共同的接纳协议，或把可用权利预先分配给副本并保护权利转移；分配总和不能超过实际资源。权利耗尽时不能继续无条件接纳。2018 综述讨论 bounded counter/escrow 方向，但本文未实现它，相关事务边界见[库存并发](../database/concurrent-inventory.md)与[聚合不变量](../architecture/domain-models-aggregates-and-invariants.md)。

## 删除只能删除它观察到的添加

普通集合只有“在/不在”，看不出一次删除针对哪次添加。为解释 add-wins 的观察删除语义，使用带永久历史的简化状态：Adds 记录 `(元素,唯一标签)`，Removes 记录被删除的标签；只有 Adds 中尚未在 Removes 的标签才使元素可见。添加创建新标签，删除记录本副本当前观察到的该元素所有存活标签；状态合并分别取并集。

这是保留历史的教学表示，便于直接检查单调性，不是优化 OR-Set 的源码。标签必须在该对象的相关历史中唯一，不能拿用户显示值代替。假设 x 的初始添加标签 a1 已在两侧可见：

| 动作 | Adds | Removes | x 是否可见 |
| --- | --- | --- | --- |
| 共同初态 | `{(x,a1)}` | `{}` | 是 |
| A 删除自己见到的 x | `{(x,a1)}` | `{a1}` | 否 |
| B 并发再次添加 x，创建 b1 | `{(x,a1),(x,b1)}` | `{}` | 是 |
| 合并两侧状态 | `{(x,a1),(x,b1)}` | `{a1}` | 是，b1 没被删除观察到 |
| 之后某副本见到 b1，再删除 x | `{(x,a1),(x,b1)}` | `{a1,b1}` | 否；旧 Adds 重放也不能复活它 |

在此契约下，并发添加保留，观察到添加后的删除则能移除它。若用户说“删除后，任何离线副本的并发重新添加也必须消失”，它要的是另一种语义；不能把 add-wins 包装成满足这个要求。

[Bieniusa 等 2012 年报告 §4](https://arxiv.org/pdf/1210.3368)给出 OR-Set 与优化方案，说明唯一标签、观察上下文及删除信息的重要性。实际实现可压缩历史或不用显式墓碑，但仍要保留必要的因果证据；不能只从可见集合里删掉 x，就声称删除已传播完整。

## 收敛不允许任意清理历史

上述教学模型中，若抹掉 Removes 的 a1/b1，却仍可能收到旧 Adds，x 就会复活。即使同时删掉本地 Adds，也挡不住旧副本或备份重放。优化需要证明相关旧状态不会再按旧身份进入，或用足够的因果上下文继续拒绝它；“已经过了一天”本身不是证明。

状态型可以发送整个状态，代价随写者、标签与历史增长；delta-state 是在相应协议下发送较小的可合并增量，不等于任意截取网络差异。加入、退出、反熵同步、持久化和恢复都会改变可安全清理的条件。对照 [Akka Distributed Data 文档](https://doc.akka.io/libraries/akka-core/current/typed/distributed-data.html)的类型、持久化与限制章节，可以看到真实库仍区分读写确认、成员清理与持久存储；本文未接入该库，也不把其配置推广成 CRDT 必需步骤。

还要区分本地内存更新、落盘、其他副本获知与业务成功确认。CRDT 合并不让邮件、支付或外部请求自动幂等，也不提供账号[授权](../../glossary/security.md#security.identity)。带 `(l,c)` 的最后写胜出规则同样需要明确取舍，时间戳边界另见[HLC](hybrid-logical-clocks-and-timestamp-boundaries.md)。

## 五道自检与核查范围

1. 收到相同更新后状态相同，与每次读取最新、最终交付、线性一致分别有什么区别？状态型与操作型对重复消息的要求为什么不能互换？
2. A 增 3、B 增 4，为什么逐分量 max 得 7，而取总数 max 和反复相加都错？哪些身份/恢复错误会破坏这个推导？
3. PN-Counter 怎样允许可见值下降而内部状态仍增长？总额 1 的例子怎样收敛到 -1？
4. A 删除 a1、B 并发新增 b1 后为什么 x 存在？后来观察到 b1 的删除又为何能让 x 消失？
5. 清理删除历史前须证明什么？合并幂等是否足以证明外部支付只执行一次、本地更新已持久化或授权成立？
