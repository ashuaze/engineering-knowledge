# CAP 与 PACELC：分区和延迟下，一次操作还能承诺什么

学习入口：两个机房断联后，为什么不能既让两侧所有读写都成功，又让它们继续表现为同一个实时更新的对象？恢复通信后把数据合并，是否就证明先前读取正确？先读[一致性与复制](consistency-and-replication.md)，理解一次写入的确认与副本传播是不同事件。

[CAP](../../glossary/distributed.md#distributed.cap) 给出特定故障模型中的不可能性；PACELC 提醒我们检查正常通信时的[延迟](../../glossary/performance.md#performance.latency-throughput)成本。使用它们之前，应先写明对象、操作、确认语义、读路径和允许的故障。只给数据库贴一个永久的“CP”或“AP”标签，无法回答某次请求究竟承诺了什么。

## 固定定义，才能讨论取舍

本文的教学对象是一个初值为 `0` 的读写寄存器 `x`：写入设置一个值，成功读取返回某次合法写入的值。先排除多对象事务、恶意节点和业务拒绝条件。

**CAP 的 C 是[线性一致性](../../glossary/distributed.md#distributed.linear-serial)。** 对已经完成的操作，要能安排一个符合对象规范的顺序；每次操作仿佛在调用与返回之间生效。如果操作甲已经返回，乙才开始，顺序中甲必须在乙之前。并发操作则可按规范选择先后。这种实时先后来自调用/返回事件，不要求各机器时钟显示一致，也不是按记录里的时间戳排序。[Herlihy 与 Wing 的原论文 §2.2](https://www.cs.cmu.edu/~wing/publications/HerlihyWing90.pdf)给出基于历史的定义。

对于尚未返回的调用，可以为其中一部分补上响应并纳入合法顺序，其余待完成调用则可省略；这样的补全仍须解释所有已返回结果并尊重实时先后。因此，不能仅因写入尚未返回，就丢掉某次已完成读取已经观察到的写入效果。

| 字母 | 本文采用的形式含义 | 不能替换成什么 |
| --- | --- | --- |
| A：可用性 | 非故障节点收到的每个请求最终完成，返回该操作规范允许的结果 | 某个百分比的成功率、固定毫秒数内返回，或一律返回“服务不可用” |
| P：分区容忍 | 要求所讨论的保证覆盖节点间任意多消息丢失、彼此不可达的执行 | “平时有网络”或一种可以让网络永不出错的配置 |

[Gilbert 与 Lynch，2002，§2–3.1](https://www.comp.nus.edu.sg/~gilbert/pubs/BrewersConjecture-SigAct.pdf)在异步网络模型中证明：即使只考虑公平执行、让非故障节点持续获得执行机会，允许上述消息丢失时，读写对象仍无法同时保证 C 与 A。其异步模型不给算法可依赖的时钟；A 也没有有限响应时间上界。因此，“要等多久才算慢”不是这一定理中 A 的定义。工程超时可以结束一次等待，却不能证明对方已故障或消息永远不会到达。

任意错误响应不能让一个寄存器实现满足 A，否则“永远报错”就能绕过问题。另一方面，合法业务请求本来就可能返回“余额不足”或条件写不成立；这是否完成了操作，要按接口规范判断，不能把所有业务否定结果都算成存储不可用。

P 是保证要面对的故障前提。若明确排除分区，讨论的是更弱的环境假设；若真的分区后服务停止，也不能声称保留了此处的 A。因此，“任意挑两个”容易遮住真正的问题：在允许失联的执行中，哪些操作还必须完成，哪些历史仍必须合法？

## 两副本断联：矛盾发生在返回历史里

下面是纸面教学历史，未执行集群实验。副本甲、乙最初均保存 `x=0`，此后两者之间的消息全部丢失；两侧节点正常执行，客户端仍能分别连接它们。客户端写入与另一个客户端后来的读取不重叠。

| 顺序 | 甲侧 | 乙侧 |
| --- | --- | --- |
| 1 | 客户端调用 `write(x, 1)` | 不收到甲侧消息 |
| 2 | 若满足 A，写入最终返回成功 | 本地仍只知道初值 |
| 3 | 写入已返回后 | 另一客户端调用 `read(x)` |
| 4 | 消息仍无法跨分区 | 若满足 A，读取最终必须完成 |

若还要满足 C，第 4 步必须返回 `1`，因为没有其他写。但乙的观察与“甲从未收到写入”的另一执行相同；在后一执行里读取应返回 `0`。乙不能靠猜测在两种执行中都正确。持续等待或拒绝这次正常读取可避免错误值，但失去了此处要求的 A；允许返回 `0` 则放弃了这段历史的 C。这是断联两侧缺乏信息的矛盾，参见[Brewer 对两节点例子的解释](https://www.infoq.com/articles/cap-twelve-years-later-how-the-rules-have-changed/)。

通信恢复后的收敛不能改变已经返回给客户端的旧值。保留线性一致性也不要求所有副本每时每刻内容完全相同：协议可以让部分副本暂时落后，同时限制从它们直接服务的读取；读写须经过哪些参与者，是实现的一部分。

## 等待、失败和未知提交是三件事

把上述历史用于接口设计时，还要区分服务端的提交事件与客户端的知识。

| 客户端观察 | 能判断什么 | 后续责任 |
| --- | --- | --- |
| 收到写成功 | 按该[接口契约](../../glossary/api.md#api.contracts)，某个确认边界已完成 | 检查成功是否覆盖持久化、复制、投影或外部副作用 |
| 收到明确失败 | 只得到该错误码和协议所承诺的信息 | 只有契约明确保证未执行，才能据此认定未提交 |
| 超时、断连或响应丢失 | 客户端没拿到确定结果 | 写入可能未提交，也可能已提交而回应丢失 |

[etcd 3.6 的“Operation completed”说明](https://etcd.io/docs/v3.6/learning/api_guarantees/#operation-completed)明确区分[共识](../../glossary/distributed.md#distributed.consensus)提交与客户端得知完成，并指出超时或网络中断可能使结果不确定。这是一个具体接口的说明，不表示所有系统的“成功”都采用相同确认阶段。

纸面反例：扣款已经提交，回应却丢失；客户端把超时当作“未扣款”，换一个请求标识[重试](../../glossary/api.md#api.retries)，可能产生第二次合法扣款。需要稳定的业务操作标识、可查询的结果状态和规定范围内的去重；仅因底层有共识，不会自动识别两次请求是同一业务意图。Raft 原论文 [§8](https://raft.github.io/raft.pdf)也用提交后回应前故障说明了重试与请求去重的必要性。等待预算与重试放大另见[超时与重试预算](../reliability/timeouts-and-retry-budgets.md)。

形式 A 不设期限；产品 [SLO](../../glossary/reliability.md#reliability.slos) 则应明确时间窗、成功判据和分母。一个系统可以在定义的请求群体内满足很高的[可用率目标](../reliability/slis-slos-and-error-budgets.md)，同时在某些分区执行中停止部分操作；这不构成 CAP 反例。

## `R + W > N` 证明相交，尚未证明读取正确

固定成员集合包含 `N` 个不同副本，成功写取得其中 `W` 个确认，读取取得其中 `R` 个响应。若 `R + W > N`，两集合必相交。这是集合计数，不包含“相交成员上的哪版可以被返回”的规则；成员变化、临时替代副本也不能未经证明就沿用同一算式。

考虑一个故意省略读回写的教学协议：`N=3`，写等待 `W=2` 个确认；读等待 `R=2` 个响应，选版本号最高的值并立即返回。三个副本初值均为 `(v0, 0)`，新写版本为 `v1`。

| 顺序 | 纸面事件 |
| --- | --- |
| 1 | 写入 `(v1, 1)` 只到甲；乙、丙尚未收到，写仍未完成 |
| 2 | 读一收到甲、丙的响应，选 `v1`，返回 `1`；不传播这个版本 |
| 3 | 读一返回后，读二才开始，收到乙、丙的响应，返回 `0` |

每次读都取得两个不同副本的响应，算式仍成立；但读一的 `1` 要求把待完成写放在读一之前，随后读二的 `0` 又无法放进合法的实时顺序。未完成写会怎样影响读，是人数口号漏掉的条件。ABD 原作者 Attiya 的[官方回顾 §3](https://hagit.net.technion.ac.il/files/2015/09/EATCScolumn.pdf)说明这种先新后旧窗口，并解释读取将所选版本写回所需集合的作用。本文没有给出完整 ABD 协议或实现证明。

共识日志同样不能仅以“收到多数响应”概括。成员、任期、日志和提交规则保护决定的历史，读取还要确认当前权威及所需状态。旧主在分区后仍自称领导者，不足以让本地读取满足 C；Raft §8 为无日志读取列出了额外条件，基于[租约](../../glossary/distributed.md#distributed.fencing)的替代还引入时钟假设。详细机制见[共识与 Quorum](consensus-leaders-and-quorums.md)及[租约与 Fencing](leases-heartbeats-and-fencing.md)。

多数侧能推进，也不表示满足形式 A：如果少数侧非故障节点收到的请求无法完成，“每个非故障节点”的要求已经不成立。多数侧自身能否及时推进还受选举、通信、持久化和调度条件约束。

## PACELC：没有分区，仍需为通信付出时间

[Abadi，2012，PACELC 一节](https://cs.umd.edu/~abadi/papers/abadi-pacelc.pdf)提出两段检查：存在分区 P 时怎样在 A/C 间取舍；否则 E，在正常运行中怎样在延迟 L 与一致性 C 间取舍。它是分析复制系统设计的框架，不是另一条与 CAP 等价的不可能性定理。

例如，写成功前等待远端所需确认，与先本地确认再传播，走的是不同通信路径；后者若允许任意副本直接读，就要面对传播期间的陈旧值。反过来，异步传播并不单独证明读一定陈旧：若读路径仍经过能够提供相应保证的协调者，或等待所需版本，就付出了相应通信或等待成本。不能只看写配置就给读结果定性。

这里要保留术语边界：Abadi 在延迟讨论中把超过典型请求超时的等待也称为不可用；这是工程上的有用区分，**不能用来改写前文 CAP 中没有响应时限的 A**。文中历史产品分类也不是对今天各版本、接口和配置的验证。

本文用 PACELC 提问，而不用它作延迟公式：要求哪种一致性，确认要等谁，读要联系哪里，在什么故障、负载与放置下衡量？实际分析应写明一致性目标；减少一些陈旧读取，不等于已经达到 CAP 的 C。通信可以通过更近放置、[批处理](../../glossary/performance.md#performance.batching)、缓存或协议设计改变；正确的租约也可能减少某条读路径的通信，但须接受其安全前提和失效等待。PACELC 不能据此推出固定的毫秒开销、性能排名，或“每次读取都必须跨机房”。

## 把保证写到操作与不变量上

下面几类问题需要分别回答，不能由一个 C 字母代答。

| 关心的问题 | 需要的概念及边界 |
| --- | --- |
| 写返回之后，另一客户端读取必须反映它吗？ | 线性一致性约束这种实时先后；重叠操作仍按对象规范排序 |
| 是否存在保留每个[进程](../../glossary/systems.md#systems.execution-units)程序顺序的共同顺序？ | 顺序一致性不额外要求跨进程非重叠操作的实时先后，见 [Lamport，1979 的定义](https://lamport.azurewebsites.net/pubs/multi.pdf) |
| 看到结果之前，是否已看到它依赖的更新？ | 因果一致性关心依赖关系；并发更新不因此获得统一实时顺序 |
| 更新停止后，副本是否会在约定传播/恢复条件下收敛？ | [最终一致性](../../glossary/distributed.md#distributed.consistency)关心最终状态，不单独承诺因果顺序、读己之写或收敛期限；因果与最终模型可结合，见 [Vogels 的作者说明](https://www.allthingsdistributed.com/2008/12/eventually_consistent.html) |
| 两条记录是否保持总额守恒，是否避免并发超卖？ | 需要[业务不变量](../../glossary/architecture.md#architecture.domain-model)及对应原子操作、约束、事务范围和隔离保证；单个寄存器的 C 不是跨记录事务方案 |

事务的可串行化讨论多个操作是否等价于某个串行事务执行；严格可串行化进一步约束事务的实时先后。不要把“[事务隔离](../../glossary/database.md#database.isolation)级别高”“每个键线性一致”和“所有业务规则已实现”视为同一个结论。前两者的区别见[线性一致性原论文 §3.3](https://www.cs.cmu.edu/~wing/publications/HerlihyWing90.pdf)，具体隔离异常见[隔离级别与 MVCC](../database/isolation-and-mvcc.md)。

作为教学决策表，可以分别规定：“订单草稿可先保存待同步”“最终扣款必须确认唯一业务操作的结果”“展示缓存可以返回带版本的旧视图”。这些是不同对象和操作的契约；保存意图不等于扣款完成，合并草稿也不等于恢复所有业务不变量。要声明允许哪些旧值/冲突、哪些操作暂停，以及恢复后怎样对账，而不是给整个产品贴一次标签。

同样，记录有可排序 ID，不代表其状态已经被所有读取路径观察到；ID 的数值顺序也不自动证明并发操作满足实时顺序。因果关系的表达见[逻辑时钟](logical-clocks-causality-and-concurrency.md)，ID 的唯一性和时间排序见[分布式 ID](distributed-identifiers-time-and-uniqueness.md)。

分区后的成员权威、日志协调和恢复选择，继续见[共识成员变更与分区恢复](membership-changes-and-partition-recovery.md)。形式模型不替代所选实现的配置生效点，也不把[灾难恢复](../../glossary/reliability.md#reliability.dr)变成原历史无损延续。

## 自检与证据范围

1. 两副本断联的历史中，哪两个调用/返回事件迫使读取返回 `1`？若乙返回错误、等待恢复或返回旧值，各改变了哪项承诺？
2. 非故障节点的一次请求十秒后成功、客户端一秒时超时，与承诺固定响应期限的可用率目标有什么区别？哪些情况下仍不能判断写是否提交？
3. `N=3`、`R=W=2` 的先新后旧例子为什么不能线性化？需要补充哪类协议规则，而不是再数一次副本？
4. 同一系统的一条查询允许旧视图，另一条查询要求实时顺序，怎样分别分析 PACELC 的两段问题？为何不能由异步复制配置或历史产品标签直接给出答案？
5. 订单状态按时间 ID 排序、每个键都能正确读取，为什么仍不足以证明扣款不重复和跨记录总额守恒？分别还需界定什么？
