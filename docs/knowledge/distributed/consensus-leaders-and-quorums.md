# 共识与 Quorum：多数响应为什么还不等于一致决定

学习入口：五个副本中有三个返回成功，就能证明它们对同一个结果达成[共识](../../glossary/distributed.md#distributed.consensus)吗？前置：复制、持久化与一致性范围。[Quorum](../../glossary/distributed.md#distributed.leadership) 是协议认可的参与集合；可靠决定还取决于成员范围、投票或日志规则、确认阶段，以及这些状态在故障后是否保留。数够响应只是其中一个条件。

## 复制、选主与共识分别解决什么

| 机制 | 主要问题 | 不能单独保证什么 |
| --- | --- | --- |
| 复制 | 将状态传播到多个位置 | [并发](../../glossary/systems.md#systems.concurrency)冲突怎样裁决，切换后保留哪一版 |
| 选主 | 哪个参与者在本轮负责协调 | 旧主已停止，候选包含已提交历史 |
| 共识 | 在规定故障模型下，对提议或日志位置形成一致决定 | 任意外部业务都一起提交，所有节点立刻应用 |
| Quorum / 法定集合 | 哪些参与集合足以满足某项协议条件 | 集合一相交就自动得到完整一致性协议 |

[Raft 原论文](https://raft.github.io/raft.pdf)将复制状态机的协议组织为选举、日志复制与安全规则。其常见故障模型是节点停止、恢复和通信异常，不是恶意节点可任意伪造响应的拜占庭模型。五节点“多数为三”的例子，也不能直接拿来推导另一种故障模型的容错数。

本文只解释关键关系，不提供可以照着实现 Raft 的完整规范；日志、选举与[成员变更](../../glossary/distributed.md#distributed.membership)需要遵守整个协议。

## 相交是集合性质，不是最新值证明

教学设定：成员集合 U 固定，包含 N 个不同副本；某次写得到 W 个成员确认，某次读联系 R 个成员。两集合都来自同一个 U，且 `R + W > N`，则它们至少有一个共同成员，否则两者并集大小会超过 N。

| 固定成员数 N | 写集合 W | 读集合 R | 可以推出什么 |
| --- | --- | --- | --- |
| 5 | 3 | 3 | 任意这样的读、写集合必相交 |
| 5 | 2 | 2 | 可以选到互不相交的集合，例如 AB 与 `CD` |
| 3 | 2 | 2 | 读、写集合必相交；两个二成员集合也必相交 |

这是纸面集合推导。共同成员可能保存多个并发版本，读操作也可能遇到尚未完成的写；仍需定义版本比较、写入与读取协议及故障恢复。即使所有写集合彼此相交，也不能仅凭人数证明线性一致。

不能把不属于该固定集合的临时替代副本、不同成员配置的响应或多个重复回执凑进同一次计数。成员变更必须保持协议要求的跨配置关系，不能各自按“我眼中的多数”独立决定。

## Raft 的多数需要配合任期与日志规则

按上述论文，在一个任期内每个成员最多投一票，候选日志须至少与投票者一样新：先比较末条日志的任期，同任期再比较末条索引，不能仅按日志长度判断。对当前任期日志，领导者可按多数复制推进提交；旧任期条目不能只因再次数到多数就直接宣布提交，而是随其后当前任期条目的提交间接提交。只记住“半数加一”，会漏掉这些安全条件。

教学场景：五成员 A–E，领导者在当前任期将某条命令复制到 A、B、C，并按完整协议提交。以后即使更换领导者，也需要维持已提交日志的安全约束；未提交的尾部则不能被客户端当作稳定结果。这不是所有副本已应用，更不是外部工单或支付已完成。

多数日志提交保护的是相应日志/状态机范围。将同一请求重发仍可能产生多个合法日志项，业务层仍需稳定操作标识与[幂等性](../api/idempotency.md)。

## 安全性与能否继续推进分开判断

[etcd 3.6 故障说明](https://etcd.io/docs/v3.6/op-guide/failures/)区分多数失效和[网络分区](../../glossary/distributed.md#distributed.partition)；下面用固定五成员配置整理其多数可达性的教学判断，不代表所有共识协议都有完全相同的恢复步骤。

| 五节点固定配置的通信情况 | 在多数协议下的教学判断 |
| --- | --- |
| 三个成员可互通并服务请求，另两个失联 | 在选举等条件满足后，三成员侧可能继续推进 |
| 分成两个二成员组和一个单成员 | 都凑不齐多数，不能靠“节点还活着”继续决定 |
| 旧主位于二成员侧 | 可能暂时仍自认为领导者，但不能据此提交新决定 |
| 之后恢复通信 | 按任期与日志规则协调，不是把两侧所有写入简单拼接 |

这里还假设相应状态正确持久化、没有超出故障模型，并且通信及调度条件足以完成协议。多数可用不等于任意[延迟](../../glossary/performance.md#performance.latency-throughput)下都能立即完成；安全性允许暂时不产生错误决定，推进还需要可用的参与者与通信条件。

多个执行者同时自认为具有权威，常被称为[脑裂](../../glossary/distributed.md#distributed.split-brain)。需要区分“自认为领导者”和“协议允许提交决定”：旧主的自我认知不必然破坏日志安全，但若外部资源仍无条件接受它的写入，就会越过共识边界。

增加副本可以改变容错与放置方案，也增加复制、存储和运维成本。五个副本如果都依赖同一台宿主机或同一[故障域](../../glossary/reliability.md#reliability.fault-domains)，并没有获得五份独立的故障隔离。

## 有领导者仍需核对读路径

读请求发给自称领导者的节点，不足以证明它仍具有当前权威，也不证明本地状态已应用到所需位置。系统需要按其协议确认读取条件；允许旧值的本地读取与要求实时顺序的读取应分别说明。

[etcd 3.6 API 保证](https://etcd.io/docs/v3.6/learning/api_guarantees/)区分默认 KV 读取保证与可允许陈旧值的 serializable 读取，也说明[超时](../../glossary/api.md#api.retries)可能让调用方无法判断操作结果。这里的 serializable 是该接口的读取选项，不能和[数据库事务](../../glossary/database.md#database.isolation)“[可串行化](../../glossary/distributed.md#distributed.linear-serial)”直接视为同一配置。

共识存储的保证也不会自动传递到应用缓存、搜索索引或外部系统。确认日志、应用状态机、返回客户端和后续投影，各自需要可观察的边界，见[一致性与复制](consistency-and-replication.md)。

多数与协议只能在对应故障和成员条件下讨论进度。断联历史、形式可用性与正常复制的等待取舍，继续见[CAP 与 PACELC](cap-pacelc-and-operation-guarantees.md)。

跨配置集合关系、非投票成员追赶、分区重连与永久失多数，继续见[共识成员变更与分区恢复](membership-changes-and-partition-recovery.md)。数据放置、配置生效和重建新集群分别有不同的接受条件。

## 用反例检查判断依据

自检：五成员配置收到了 A 的三次重试响应，是否有三个成员确认？`AB` 与 `CD` 各自保存一版，为什么不能靠“都有副本”判断哪版已提交？旧任期日志已在多数节点，为什么还要检查提交规则？

可先画出成员集合、任期、日志位置、确认阶段与调用开始/返回，再判断某条结论是否越过了协议边界。真正验证还需集群故障注入与历史检查，不能用一张时序表替代。
