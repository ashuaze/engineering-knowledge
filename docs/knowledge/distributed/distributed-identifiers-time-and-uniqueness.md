# 分布式 ID：唯一、可排序与业务只执行一次分别依赖什么

学习入口：订单 ID 换成了 [UUID](../../glossary/distributed.md#distributed.uuid)，为什么[重试](../../glossary/api.md#api.retries)仍创建两笔订单？编号里带时间，为什么排序后仍看不出谁先提交？ID 主要用于识别；唯一性、生成顺序、业务去重与权限是不同契约，必须分别说明范围和成立条件。

前置：[逻辑时钟与因果关系](logical-clocks-causality-and-concurrency.md)、[幂等性](../api/idempotency.md)。本文比较集中序列、Twitter 历史 Snowflake 实现、RFC 9562 的 UUIDv4/v7 和 [ULID](../../glossary/distributed.md#distributed.ids) 作者规范；不把“分布式 ID”当成一种固定格式，也不推荐未经目标环境核查的生成器。

## 先写下唯一性要覆盖谁

“不重复”至少要指明对象类型、租户、环境、地域、时间范围，以及[灾难恢复](../../glossary/reliability.md#reliability.dr)后是否仍与旧 ID 共存。两个系统各自从 1 开始，在各自库内可能唯一，合库后却会冲突；把测试数据导入生产、恢复旧生成器快照，也可能扩大原来的比较范围。

| 方案 | 主要怎样避免冲突 | 额外依赖 |
| --- | --- | --- |
| 集中序列或号段 | 同一权威分配状态不重复分配 | 访问与故障恢复协议、号段互斥、边界不回绕 |
| 经典 Snowflake | 时间、节点身份、同时间片序列的组合不复用 | 节点号分配、时钟与[进程](../../glossary/systems.md#systems.execution-units)状态 |
| UUIDv4 | 从较大随机空间取样，降低碰撞概率 | 随机质量、生成状态与碰撞处置 |
| UUIDv7 / ULID | 时间前缀加随机或局部单调状态 | 同时间片行为、随机质量、具体库及恢复策略 |

前两种可以在明确条件下按不重叠分配证明唯一，后两类常采用概率模型或混合状态；都不能省略实现与运行前提。统一编码、保留完整位宽和明确比较规则也属于契约，截短字符串或只取低位会改变冲突空间。

## 集中序列给出分配次序，不给出提交次序

权威分配器可以原子推进计数器，也可一次发放不重叠号段供本地消耗。号段减少逐次调用，却增加未用号码、状态恢复和分配者身份的管理；把同一号段复制到两个恢复实例，会破坏证明。

[PostgreSQL 18 的序列说明](https://www.postgresql.org/docs/18/functions-sequence.html)规定并发 `nextval` 原子取得不同值，也明确事务回滚不会回收该次取号，因此可能有空洞；若号码要持久用于数据库之外，应先确认对应取号已提交。不能把数据库内的一次调用保证推广到独立复制出的序列、人工重置、循环配置或错误故障切换。

纸面例：T1 取得 10 后等待，T2 取得 11 并先提交，T1 随后提交或回滚。因此 `10<11` 不能说明 10 已先提交，也不能从缺号推断数据丢失。集中化还引入服务可达性与接管依赖；跨故障后的唯一性需要保护分配状态，而非只让每个进程各自递增。

## 经典 Snowflake 的位数是特定布局预算

本文固定参照 Twitter 归档仓库的 [`snowflake-2010` / `IdWorker.scala`](https://github.com/twitter-archive/snowflake/blob/snowflake-2010/src/main/scala/com/twitter/service/snowflake/IdWorker.scala)，不是所有同名产品。按非负有符号 64 位布局解释，其预算为：

| 部分 | 位数 | 含义 |
| --- | --- | --- |
| 保留符号位 | 1 | 保持该正数布局的表示契约 |
| 时间差 | 41 | 相对 epoch 的毫秒数；该实现 `twepoch=1288834974657` |
| 数据中心号 + 工作者号 | `5+5=10` | 最多 `32×32=1024` 种节点组合 |
| 同毫秒序列 | 12 | 每个节点组合、每个毫秒至多 `2^12=4096` 个序列值 |

这些是编码空间的上界，不是实测吞吐；`2^41` 毫秒约 69.7 年是相对 epoch 的时间预算，不是部署日起无限续期。该历史实现对同一个 `IdWorker` 实例的 `nextId` 串行化，检测到时间小于该实例上次时间时拒绝，序列耗尽则等待后续毫秒。它的内存状态与传入节点号本身不构成跨重启、跨实例的完整协调协议。

### 纸面小布局可以暴露复用

为便于复算，另设一个 **8 位教学格式**：4 位时间片 `t`、2 位节点号 `w`、2 位序列 `s`，`ID=16t+4w+s`。时间片单位是本例的 tick，不是实际 Snowflake 的位宽或性能配置。

| 情形 | `(t,w,s)` | ID |
| --- | --- | --- |
| 节点 1 在 tick 5 首次生成 | `(5,1,0)` | 84 |
| 同节点继续生成 | `(5,1,1)`、`(5,1,2)`、`(5,1,3)` | 85、86、87 |
| 同 tick 的节点 2 | `(5,2,0)` | 88 |
| 节点 1 等到 tick 6 后重置序列 | `(6,1,0)` | 100 |
| 旧状态丢失，在 tick 5 再次从 0 开始 | `(5,1,0)` | 再次为 84 |

本例同 tick 第五次请求不能将序列静默绕回 0；可按设计等待、拒绝或切换有明确隔离的新命名空间。时间达到 16 也已超出 4 位预算，截成 0 会复用历史空间。等待与拒绝都影响可用性，不能同时无条件承诺永不重复、任意速率与立即返回。

等到 tick 6 也只在状态或高水位保证不会重新分配已用组合时安全；表中的 100 假定此前未分配。tick 6 不是一劳永逸的安全点，恢复协议仍须覆盖后续回拨和重启。

### 节点号与恢复状态必须一起管理

| 故障或变更 | 必须保留的约束 |
| --- | --- |
| 工作者暂停后，节点号被转给新进程 | 旧进程不能继续用同一身份生成并发布号码；分配记录改变不等于旧进程已停止 |
| 重启、[容器](../../glossary/devops.md#devops.containers)克隆或恢复快照 | 不复用仍可能与旧输出重合的时间、节点、序列组合；需要持久高水位或经证明的重新分配策略 |
| 时钟回拨或校时 | 明确等待、拒绝或逻辑推进规则，并处理其状态寿命，不能直接清零序列 |
| 跨 Region、合库或恢复副本重新上线 | 节点命名空间在实际共存范围内不冲突，恢复不能带回已退役身份或旧号段 |
| 时间字段耗尽或更换 epoch | 迁移格式与比较协议；不同 epoch 的相同字段不自动代表同一时间 |

这些是从字段不复用条件推导的设计义务，不是声称归档实现已经提供它们。节点号采用租用机制时，应参照[租约与 Fencing](leases-heartbeats-and-fencing.md)处理旧执行者；若新代次不编码进 ID，也没有在发布路径执行约束，仅在协调库登记新持有者不能自动防止重复。

## UUIDv4 与 UUIDv7：格式、随机和局部单调分开看

[RFC 9562 §5.4、§5.7 与 §6.2](https://www.rfc-editor.org/rfc/rfc9562.html)给出以下区别；二者均为 128 位 UUID：

| 版本 | 字段 | 可以怎样解释 |
| --- | --- | --- |
| UUIDv4 | 4 位版本、2 位变体，其余 122 位随机数据 | 不含生成时间，不提供时间排序 |
| UUIDv7 | 高 48 位 Unix 毫秒时间，4 位版本、2 位变体；另有 `rand_a` 12 位与 `rand_b` 62 位 | 时间前缀有利于按编码时间排序；纯随机尾部时，同毫秒内不保证生成顺序 |

版本字段固定为二进制 `0100`（v4）或 `0111`（v7），两者变体均为 `10`。v7 的字段顺序是 `48位时间 + 4位版本 + 12位rand_a + 2位变体 + 62位rand_b`；74 位可用空间被变体位分隔，不能当成一段连续字段。

v7 的 74 位空间不必全部是独立随机位：规范允许按顺序放入可选的子毫秒时间片段（最多 12 位）、适当初始化的计数器，再以随机数据填剩余空间。库是否采用这些方案、作用于哪个生成器状态，必须单独查明；不能给所有 v7 一律套用“74 随机位”或“进程内严格单调”的保证。

规范的 §6.9 建议使用 CSPRNG，并注意 fork 等状态变化；“使用了随机函数”不等于质量足够。比如 [Python 3.13 `secrets`](https://docs.python.org/3.13/library/secrets.html)把安全随机用途与模拟用 `random` 区分开。此处仅说明随机源责任，不提供自制 UUID 算法，也不声称某个库已通过跨实例验证。

## ULID 的字符顺序与单调工厂有局部范围

[ULID 作者规范](https://github.com/ulid/spec)规定 48 位 Unix 毫秒时间加 80 位随机部分，使用 Crockford Base32 编码为 26 字符；它不是 RFC 9562 的一种 UUID 版本。`26×5=130` 位承载 128 位，编码空间有多余高位，超过 128 位的值应拒绝，不能截断；规范给出的最大编码以 `7` 开头、余下为 `Z`。

规范的默认形式不保证同毫秒排序；单调工厂检测同毫秒后，对随机部分按最低位加一并进位，溢出则失败。这个递增只涉及共享该工厂状态的调用；多进程、多个工厂或重启不会自动共享它，也不能因此证明全局唯一或全局生成次序。起始随机值靠近上界时，还可能在远少于 `2^80` 次调用后溢出。回拨和状态恢复的具体行为仍需核对所选库。

ULID 规范的文本表示大小写不敏感；解析接受合法字母的大小写形式后，应先归一到规范大写并校验固定 26 字符宽度，再按规范默认 ASCII、从左到右的字节字典序比较。任意语言或数据库的排序规则不保证产生同一顺序。格式兼容也不意味着可以把 UUID 字符串、ULID 字符串与十进制 Snowflake 字符串混在一起，得到统一时间序。

## 概率结论先说明取样模型

教学模型：在同一碰撞空间内生成 n 个值，每个值都独立、均匀地从 `2^b` 个可能值取样。任一对相等的概率为 `1/2^b`，对全部 `n(n−1)/2` 对应用并集上界，可得：

```text
P(至少一次碰撞) ≤ min(1, n(n−1) / 2^(b+1))
```

例如人为缩成 `b=20`，生成 `n=100` 个值，上界为 `4950/1048576≈0.00472`，约 0.472%。这是概率上界，不是观测到的碰撞率，更不是实际 UUID/ULID 的参数。v7/ULID 需先确定同一时间前缀内哪些生成器共享随机空间；可选计数和随机相关性会改变模型，不能直接套总位数。

伪随机状态被克隆、固定种子、截位、错误编码或多个节点重复计数，都可能违反假设；小碰撞概率不能证明这些实现问题不存在。数据保存边界还应按需要设置有效范围的[唯一约束](../../glossary/database.md#database.constraints)，并定义冲突后是否拒绝、重新分配或调查；若冲突实际来自同一业务动作重试，盲目换 ID 又会制造重复业务。

## 排序、幂等、权限和索引各有契约

主键是存储模型中的行身份与约束角色，生成一个候选 ID 不会自动创建行唯一约束，也不定义业务操作身份。应显式建立所需约束并核对其检查范围，见[数据模型与约束](../database/data-models-and-access-patterns.md)。

时间型 ID 反映的是生成器使用的时间和低位规则；[时钟偏差](../../glossary/distributed.md#distributed.clocks)、同毫秒并发、预分配和提交等待都会让 ID 顺序不同于真实先后或提交顺序。它也没有自动传播因果信息，不能替代[逻辑时钟](logical-clocks-causality-and-concurrency.md)或作为全局提交位置。

同一创建请求每重试一次都生成新的唯一 ID，仍会得到两笔不同记录。业务[幂等](../../glossary/api.md#api.idempotency)键需要在定义的身份、动作和保留期内稳定关联原结果；随机 UUID 可以承载这个键，却不能替代[幂等协议](../api/idempotency.md)。对象标识再难猜，也不能替代[对象级授权](../security/object-level-authorization.md)。

顺序较集中的 ID 可能改变索引局部性，也可能把范围[分片](../../glossary/database.md#database.partitioning)的新写入集中到尾部；随机 ID 则有不同的访问分布。结果依赖[数据库索引](../../glossary/database.md#database.indexes)结构、键宽、写入模式、[分片键](../../glossary/database.md#database.shard-key)与存储配置，不能承诺换成某格式就更快或更安全。继续读[分区、分片与数据路由](../database/partitioning-sharding-and-data-routing.md)，[一致性哈希](consistent-hashing-placement-and-rebalancing.md)决定放置变化的性质，并不提供 ID 唯一性。

当分配服务在网络故障下无法确认当前权威或安全节点身份，拒绝发号与允许本地概率生成有不同前提；可对照本批 [CAP/PACELC 与操作保证](cap-pacelc-and-operation-guarantees.md)检查所承诺的范围，不能从 ID 的格式单独推导 [CAP](../../glossary/distributed.md#distributed.cap) 结论。

## 自检与核查范围

1. 两个 Region 的节点都配置同一工作者组合号，为什么本地序列各不重复仍不够？
2. 小布局中为什么 `(5,1,0)` 在重启后会再次生成 84，等待到 tick 6 又依赖什么状态？
3. UUIDv7 在同一毫秒内必然递增吗，74 位空间在不同合法实现中一定全是随机位吗？
4. ULID 的 26 个 Base32 字符为什么不能接受任意 130 位值，单调工厂能否跨进程维持同一顺序？
5. 若重试每次得到新的唯一 ID，为什么仍需幂等记录、唯一约束和当前对象权限检查？
