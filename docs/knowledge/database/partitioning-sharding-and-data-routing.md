# 分区、分片与数据路由：一次查询需要访问哪些数据

学习入口：数据已经分到八个节点，为什么按订单号查询仍慢，新增节点后[热点](../../glossary/performance.md#performance.contention)也没消失？拆分数据只改变放置与管理单位。一次请求能缩小到哪些数据，还取决于查询谓词、[分片键](../../glossary/database.md#database.shard-key)、路由元数据和结果语义；每片更小不等于每次请求只查一片。

前置：[索引与执行计划](indexes-and-query-plans.md)、[事务隔离与 MVCC](isolation-and-mvcc.md)。本文固定参照 PostgreSQL 18 声明式表[分区](../../glossary/database.md#database.partitioning)与 MongoDB 8.0 分片机制，并用抽象模型对比路由策略；不将它们的约束和迁移步骤互相套用。这里的“分区”指数据拆分，不是节点失联的[网络分区](../../glossary/distributed.md#distributed.partition)。

## 拆分与复制分别改变什么

一张逻辑表可以按规则形成多个数据子集；物理实现还决定这些子集由哪些表、文件、节点或分片组承载。逻辑边界与机器数不必一一对应：一个节点可以拥有多个区间，一个分片也可以由多个副本共同保存。

[PostgreSQL 18](https://www.postgresql.org/docs/18/ddl-partitioning.html)把声明式分区父表作为没有自身存储的逻辑入口，数据存放在各分区中；常见本地分区并不因此变成跨节点数据库。MongoDB 8.0 的[每个 shard 保存部分数据，并以副本集部署](https://www.mongodb.com/docs/v8.0/core/sharded-cluster-shards/)，说明拆分与复制可以组合：前者决定哪一部分数据归谁，后者决定同一部分保留几份以及怎样容错。片内读取哪个副本及它有多新，继续按[一致性与复制](../distributed/consistency-and-replication.md)判断。

例如“四个分片，每片三副本”不是十二个互不重叠的数据范围。它有四个数据归属组及十二个副本成员；实际是否分布在十二台机器，还取决于部署。增加副本也不会自动把单个热写键拆给多个独立写入分片。

## 路由规则与分片键

以下是教学策略分类，实际系统常把几种方式组合使用：

| 策略 | 怎样找到目标 | 适合利用的局部性 | 主要代价或边界 |
| --- | --- | --- | --- |
| 范围 | 键落入哪个半开区间，就查对应分区及其当前归属 | 连续时间、编号等范围访问 | 单调新增可能集中写当前尾部；跨范围要访问多个目标 |
| 哈希 | 对键计算约定哈希，再按桶或哈希范围映射 | 相等键访问，分散不同键 | 原始键连续不代表哈希结果相邻；同一热键仍落到同一归属 |
| 目录 | 查“租户或分区单元 → 当前分片”的显式映射 | 可单独迁移某些数据单元 | 元数据[可用性](../../glossary/reliability.md#reliability.availability)、缓存更新与变更协议成为依赖 |

分片键不是“随便挑一个已有索引”。主键主要表达身份与唯一性；索引提供片内访问路径；分片键参与数据放置和目标选择；权限条件限制主体能访问哪些数据。字段可以重合，职责仍不同。按 `tenant_id` 定向到某片，不表示请求者已获该租户[授权](../../glossary/security.md#security.identity)；只带 `order_id` 查到片内索引，也不表示路由器知道它在哪片。

选键应一起看不同取值数、重复频率、写入随时间的分布和常见查询。MongoDB 8.0 的[选键说明](https://www.mongodb.com/docs/v8.0/core/sharding-choose-a-shard-key/)分别讨论基数、频率与单调变化：高基数并不单独保证均衡，同一高频键与单调写入都可能形成瓶颈。组合键可以增加拆分维度，但后缀的分散收益和前缀查询的扇出也必须一起评估。

纸面热点：假定每秒 12,000 次请求，某租户占 70%，所有该租户数据按单独的 `tenant_id` 值归到一片，则该片先承受 `12,000×0.7=8,400` 次/秒。若该片在指定工作负载下只能承担 4,000 次/秒，增加其他空片并不能消除这项瓶颈。这些容量数字是教学假设，未做压测。要改变它，需要改变该租户数据或请求的分散单位、访问模型或业务接纳策略；仅把一个范围拆成同片上的小块也没有增加执行容量。

## 范围边界与目标集合的纸面推演

设键 `k` 为整数；下表中的区间统一采用 **包含下界、不包含上界** 的 `[a,b)`。P0–P2 是逻辑数据单元，A、B 是抽象的分片归属组。此表不是 PostgreSQL 自动跨节点分片的配置。

| 数据单元 | 键范围 | 当前归属 |
| --- | --- | --- |
| P0 | `[0,100)` | A |
| P1 | `[100,200)` | B |
| P2 | `[200,300)` | A |

| 查询条件 | 可能包含结果的数据单元 | 不重复的目标分片集合 |
| --- | --- | --- |
| `k=100` | P1 | `{B}` |
| `100≤k<200` | P1 | `{B}` |
| `90≤k<210` | P0、P1、P2 | `{A,B}` |
| 只按其他非路由字段过滤 | 不能由本表排除任一单元 | `{A,B}` |

因此 100 归 P1，200 归 P2，300 不属于表中任何范围；若这是完整写入路由且没有默认分区，就必须有明确的拒绝或补建规则。跨范围查询访问三个数据单元，但只有两个归属组；实际请求和连接数量还受执行器[批处理](../../glossary/performance.md#performance.batching)、分页、重试等影响，不能把表中的集合大小当成精确网络包数。

若改为教学伪函数 `H(k)=k mod 4`，四个桶 B0–B3 各在不同分片，则 `k=100` 定向 B0；范围 `18≤k<22` 涉及 18、19、20、21，余数为 2、3、0、1，四片都要访问。这个伪函数仅为可复算示例，**不是 PostgreSQL 或 MongoDB 的默认[哈希函数](../../glossary/algorithms.md#algorithms.hash-table)或部署建议**。成员变化时怎样减少重新映射，见[一致性哈希与数据放置](../distributed/consistent-hashing-placement-and-rebalancing.md)。

## 裁剪、定向与片内索引是三步

PostgreSQL 18 的[分区裁剪](https://www.postgresql.org/docs/18/ddl-partitioning.html#DDL-PARTITION-PRUNING)使用分区边界排除不可能匹配的分区，可以发生在计划或执行阶段；它不依赖分区键上存在索引。留下的分区仍需选择索引扫描或顺序扫描。谓词是否能与边界对应、参数何时已知和[执行计划](../../glossary/database.md#database.plans)如何表示，都应核对；“在 `WHERE` 写了分区列”不是任意表达式都能有效裁剪的保证。

跨节点还需知道数据当前在哪。MongoDB 8.0 的 [`mongos` 路由说明](https://www.mongodb.com/docs/v8.0/core/sharded-cluster-query-router/)描述了从配置服务器缓存元数据、选择目标分片并合并结果的过程。相应分片键或前缀谓词可能缩小目标；缺少所需路由条件时会广播，包含分片键的宽条件也可能涉及全部分片。这里的索引支持、谓词和元数据各有作用，不能把“片内查询很快”当作“全局不会扇出”。

如果 1,000 次用户查询每次都访问八片，基础扇出是 8,000 次片级查询，而不是集群只处理 1,000 次本地工作；还没计算重试、多个游标批次和复制。[并行](../../glossary/systems.md#systems.concurrency)执行可以降低部分工作负载的耗时，也增加总工作量、连接、合并内存和对慢片的依赖。加片能否获益取决于访问方式和瓶颈，不能承诺线性加速。

完整结果必须覆盖契约要求的全部目标。某片超时后，剩余片的结果只能是已覆盖子集，不能悄悄作为全局总数或完整榜单返回。接口应明确是整体失败、允许并显式标识部分结果，还是改走满足保证的查询路径；恢复与重试还需防止重复合并和混用不兼容的数据视图。

## 扇出、结果合并与跨片约束

纸面 [Top-K](../../glossary/algorithms.md#algorithms.trees)：固定一个共同的数据视图，三个分片持有互不重复的记录，全部使用同一严格排序规则，例如“分数降序，再按唯一 ID 定序”。过滤已经在片内完成，各片候选如下：

| 分片 | 本片前三名的分数 |
| --- | --- |
| A | 99、95、60 |
| B | 98、96、70 |
| C | 97、94、80 |

每片发回前三名，协调者从至多 `3×3=9` 个候选取全局前三名，得到 99、98、97。某记录若连本片前三名都进不了，至少有三条同片记录排在它前面，因此不可能成为全局前三名；证明依赖共同排序和完整候选。任意只问一片、每片只取一条后直接当作通用 Top-3，或遗漏超时片，都没有相同保证。

上表恰好每片第一名就是全局前三名，但换成 A 的前三名为 99、98、97，B、C 的最高分分别为 96、95，每片只取一条便只得到 99、96、95，漏掉全局第二、第三名。这说明候选数需要由排序语义保证，不能依赖一次数据分布的巧合。

该推导不直接适用于“跨片先按商户求销售额再排名”：同一商户可能在多片，必须先正确合并分组值。分页也需全局顺序、稳定的并列处理和约定的数据视图；每片各跳过相同偏移不等于全局跳过。更详细的游标与变动边界见[契约与分页](../api/contracts-and-pagination.md)。上表是算法推演，不声称某产品永远只传九条记录。

约束也不能仅从片内扩大：

| 需求 | 必须核对的范围 |
| --- | --- |
| 全局唯一 | 唯一检查是否覆盖所有可能存放同一身份的数据单元，或由放置规则确保同键共置 |
| 跨片[外键](../../glossary/database.md#database.constraints) | 父子是否共置，产品是否提供相应约束，删除与并发更新如何协调 |
| 跨片事务 | 是否使用支持的[分布式事务](../../glossary/distributed.md#distributed.2pc)机制，其读写保证、提交和故障恢复条件是什么 |
| 全局聚合与联接 | 哪些运算能下推，哪些数据需传送、重分组和合并 |

具体规则有产品边界。PostgreSQL 18 声明式分区上的主键或唯一约束要求包含所有分区键列，且分区键不能含表达式或函数；这是其分区索引检查范围的限制，见[声明式分区限制](https://www.postgresql.org/docs/18/ddl-partitioning.html#DDL-PARTITIONING-DECLARATIVE-LIMITATIONS)。例如按月份拆分后，`UNIQUE(月份,id)` 约束的是二者组合，不会顺便保证 `id` 跨月份唯一。

MongoDB 8.0 的[分片键与唯一索引规则](https://www.mongodb.com/docs/v8.0/core/sharding-shard-key/)对范围分片集合允许的唯一索引要求分片键作为相应前缀，并有 `_id` 的特别边界：`_id` 不是分片键时，其默认唯一索引不能单独保证跨片唯一；哈希索引也不能加唯一约束。这些规则不应改写成“分片系统一律不能唯一”。

同样，[MongoDB 8.0 支持跨片事务](https://www.mongodb.com/docs/v8.0/core/transactions/)，但其保证仍需按读写关注设置和具体操作核对，且分布式协调有成本；不能从某个本地事务直接推导所有外部读取会同时看到各片提交效果。跨参与者决定与业务恢复的区别见 [2PC、Saga 与补偿恢复](../distributed/two-phase-commit-sagas-and-recovery.md)。

## 迁移、切换与恢复

增加节点只是提供新位置。MongoDB 8.0 的[平衡机制](https://www.mongodb.com/docs/v8.0/core/sharding-balancer-administration/)会按数据分布和条件迁移范围；其文档明确区分复制存量、同步迁移期间变化、更新归属元数据及清理旧副本。它有带宽、执行与清理成本，不是改变一条映射就搬完数据；均衡数据量也不证明请求热度均衡。

审阅通用迁移设计时，可以沿下列问题核对；这是教学检查表，不是手动实现某产品迁移的操作步骤：

| 阶段 | 需要的证据 |
| --- | --- |
| 登记迁移 | 源、目标、数据范围与配置视图或代次明确；旧路由和并发变更有处理规则 |
| 复制与追赶 | 存量与期间新增、更新、删除都有可恢复的接续，旧回填不能覆盖新状态 |
| 切换 | 目标达到约定完成边界，持续写路径已接续；在途请求、迟到旧写和路由缓存有明确行为 |
| 回退 | 旧位置仍满足回退目标；切换后的新增变化能补齐，或明示无法无损回退 |
| 回收 | 无仍依赖旧位置的读写与恢复任务，修复及回退窗口结束后才清理 |

例如 `[100,200)` 从 B 搬到 C，复制完 150 号记录后该记录被删除，若删除未接续，C 会保留幽灵记录；若路由已指向 C、C 尚缺一半存量，查询也不能靠“目录已更新”补回数据。暂停写入、日志追赶、版本比较、转发或其他方案必须形成完整协议，单独双写仍有部分成功窗口。

重新定义分片键还会改变共置、唯一性和常见查询的目标集合，不能只按新机器的容量评估。结构与混合版本兼容继续读[数据库迁移](schema-migrations-and-compatibility.md)，模型与访问路径选择见[数据模型与访问模式](data-models-and-access-patterns.md)。本文聚焦路由、约束与迁移的连接，不重复展开[一致性哈希](../../glossary/distributed.md#distributed.hashing)算法。

分片后的读写取舍见[CAP 与 PACELC](../distributed/cap-pacelc-and-operation-guarantees.md)，记录身份的生成范围见[分布式 ID](../distributed/distributed-identifiers-time-and-uniqueness.md)。路由与编号格式不能代替跨片唯一约束、提交或权限保证。

## 自检与核查范围

1. 纸面范围表中 `k=200` 与 `90≤k<210` 分别访问哪些数据单元和分片？
2. 为什么[分区裁剪](../../glossary/database.md#database.partition-pruning)成功，留下的分区仍可能顺序扫描；片内有索引又为何不能保证单片查询？
3. 一个租户占 70% 请求时，增加空分片为什么可能无法降低该租户所在片的负载？
4. 取各片 Top-3 再合并的证明依赖什么；分组聚合、分页或超时为何需要另行处理？
5. 新路由已经发布，为什么仍需证明增量、删除、回退与旧位置回收的状态？
