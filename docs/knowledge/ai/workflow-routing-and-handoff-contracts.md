# 路由与交接契约：下一步交给谁，责任怎样转移

学习入口：客服助手说“已转给技术专家”，原助手可以立即把任务标为完成吗？前置：[工具调用](../../glossary/ai.md#ai.tools)、可信身份与结果核实。[路由](../../glossary/ai.md#ai.planning)决定下一条处理路径，交接还要说明谁继续推进、带走哪些信息、怎样返回结果，以及接收失败时谁负责。模型说出目标名称，只是一份待校验的候选。

## 先区分四种调度决定

| 决定 | 解决的问题 | 不自动带来什么 |
| --- | --- | --- |
| 规划 Planning | 目标可拆成哪些子任务、依赖是什么 | 每个子任务可执行或已经获准 |
| 路由 Routing | 当前输入进入哪条允许的处理路径 | 目标具备权限，或者分类判断正确 |
| 委派 Delegation | 让一个处理单元完成子任务并返回 | 原协调者的汇总责任已经结束 |
| 交接 Handoff | 后续由哪个角色或状态继续接手 | 旧动作已完成、凭证可转交或全流程成功 |

[LangGraph 的工作流说明](https://docs.langchain.com/oss/python/langgraph/workflows-agents)分别展示预设链路、路由和动态分解子任务等模式。这些是组织控制流的方法，不要求每一步都由模型决定；明确的前提校验和权限判断可以由确定规则完成。

交接也不一定需要另起[进程](../../glossary/systems.md#systems.execution-units)或增加一个模型。[LangChain Handoffs](https://docs.langchain.com/oss/python/langchain/multi-agent/handoffs)包含同一 Agent 按持久状态切换配置，以及不同子图之间移交的实现。本文讨论通用责任契约，不把该框架的状态字段当成所有产品的统一协议。

## 目标名称不能替代准入检查

教学链路为：输入及可信作用域 → 路由候选 → 目标白名单与前置条件 → 当前[授权](../../glossary/security.md#security.identity)与预算 → 建立委派或交接记录 → 调度目标。没有合适目标、关键条件不明、候选不完整时，应有澄清、保留待办或停止分支，不能默认开放任意目标。

例如“账单异常”可能需要解释费用，也可能需要发起退款。可以先进入账单解释路径，写操作仍由独立业务规则与审批控制；分类为 refund 并不等于允许退款。路由理由和置信度有助于诊断，却不是授权依据，详见[工具授权](tool-authorization-and-untrusted-results.md)。

增加专业角色可能改善上下文聚焦，也增加分类错误、跨角色往返、协议维护与费用。能用一个明确状态切换完成的流程，没有必要仅为“看起来智能”拆成多个角色；是否拆分取决于能力、数据和责任边界。

## 交接材料要支持继续行动

下面是教学交接清单，不是可直接提交给某 SDK 的完整对象：

| 材料 | 应表达什么 |
| --- | --- |
| 任务 ID、父任务与交接 ID | 属于哪个目标，重复交接怎样识别 |
| 目标、允许的职责与完成条件 | 要回答、调查还是执行；什么证据算完成 |
| 当前事实及来源、版本 | 已核实什么、哪些只是推断、哪些条件仍有效 |
| 已执行及未知动作 | 稳定 operation_id、当前结果状态、查询或人工处理入口 |
| 可见数据与能力范围 | 由可信[运行时](../../glossary/runtime.md#runtime.virtual-machine)绑定的身份、租户和当前授权；不传原始凭证冒充授权 |
| 剩余预算、期限与回传约定 | 接收方还能做什么，结果交给谁，失败如何升级 |

摘要需要保留否定、未知、版本和来源。“工单创建调用[超时](../../glossary/api.md#api.retries)，结果未知”不能压缩成“待创建工单”，否则接收方可能再次创建。声明的完成状态应关联[可核实工具结果](tool-calling-and-execution-contracts.md)，不能只依据前一个角色的自然语言总结。

接收方应只拿到完成职责所需且有权读取的信息。传递消息历史时，还需保持实际模型协议要求的调用与结果关联；上述 Handoffs 文档对其子图示例明确要求相应消息配对。按协议补全记录不等于允许复制全部历史或提高外部文本的指令优先级。

## 接收、完成与回传分别确认

教学状态可以采用 offered → accepted → working → returned，另设 rejected、unknown 等分支；这些名字只用于解释。accepted 至少需要对应可信的接收依据，不能把一句“我已接手”或网络发送成功直接当成可靠存储与唯一执行权。

| 观察 | 协调者应保留的判断 |
| --- | --- |
| 请求未获接收确认 | 交接结果未知，按交接 ID 查询或安全重投 |
| 接收已确认，目标还在处理 | 尚未完成；明确当前责任人与等待方式 |
| 返回部分证据，依赖仍失败 | 标记部分完成及缺口，按汇总规则继续或停止 |
| 返回成功文字但没有约定证据 | 结果待核实，不能直接关闭父任务 |

同进程状态切换与跨服务交接需要不同实现。跨服务中，持久化交接记录、可靠派送、重复接收去重，以及旧执行者的停用要分别设计；需要排除旧执行者写入时，还须让权威边界检查有效执行代次。仅设置 active_agent 或发送停止消息，不会自动形成分布式唯一所有权。

委派后原协调者通常继续负责整合，交接则需要明确新的推进责任。两者都不能把子任务的“已收到”当作父目标的“已完成”。

## 循环与并行都需要收口

A 认为应交给 B，B 又认为应交给 A，是没有进展的循环。可记录交接次数、目标与问题状态指纹，遇到重复且没有新增证据时澄清或升级；仅比较[提示词](../../glossary/ai.md#ai.instructions)文本可能漏掉同义往返，因此还需要总预算作为硬边界，见[持久化预算](durable-budgets-and-failure-convergence.md)。

[并行](../../glossary/systems.md#systems.concurrency)委派前，应先判断子任务是否独立、是否会写同一对象，返回后怎样合并冲突。两份答案一致不证明来源独立；一个任务完成也不意味着其他任务自动取消。父任务结束时，还需说明在途工作及其可能产生的效果。

## 纸面推演与自检

教学场景：技术角色提交工单后丢失回执，交接给协调者；协调者看到的材料应包含该动作的 unknown 与稳定标识。下一步先按契约查询、[幂等](../../glossary/api.md#api.idempotency)核实或人工对账，不能因换了角色就重置动作身份。若查询权限已撤销，保留未知并停止相应访问。

自检：发送交接请求后超时，能否立即分配一个新交接 ID？为什么“转给管理员角色”不产生管理员权限？接收角色缺少来源或当前版本时，应该补查什么？
