# 持久化预算与失败收敛：恢复以后怎样避免无限重试

学习入口：每个角色最多尝试三次，为什么整个 Agent 仍可能一直[交接](../../glossary/ai.md#ai.planning)和[重试](../../glossary/api.md#api.retries)？前置：流程状态、工具语义与[重试预算](../../glossary/reliability.md#reliability.retry-budget)。限制需要跟随同一个任务跨越子任务和恢复，而不是每创建一个对象就获得一份新额度。所谓失败收敛，是让系统走向可解释的完成、停止或人工处理状态，不是保证最终一定成功。

## 一个“最大次数”约束不了所有资源

| 预算维度 | 需要明确的计数口径 | 容易遗漏的工作 |
| --- | --- | --- |
| 流程步骤、交接与深度 | 哪次决策或控制转移算一步 | A、B 互相转交，每个局部循环都没超限 |
| 调用尝试与重试 | 首次是否计入，模型和工具是否分账 | 参数修复、状态查询、SDK 内部重试 |
| 总期限与单次时限 | 根任务何时截止，等待是否计入 | [排队](../../glossary/performance.md#performance.queueing)、审批等待、退避和恢复后的时间 |
| [并发](../../glossary/systems.md#systems.concurrency)与排队 | 哪些已派送或仍在执行的工作占名额 | 本地超时后远端继续运行 |
| [Token](../../glossary/ai.md#ai.context)、费用与其他配额 | 预计值、预留和结算分别如何算 | 失败调用仍计费，回执丢失后的未知用量 |

以上限制应分别定义；步骤少不表示费用低，Token 上限不表示外部工具已停止。若应用看不到 SDK 内部尝试，就不能把外层调用计数称为完整物理请求上限。

[AWS 对重试与退避的说明](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)指出，重试会增加下游负载，多层独立重试还会放大尝试数。Agent 的模型修复、工具重试和工作流恢复也需要明确责任层，不能各自凭局部成功率不断加码。本文的共享预算设计是工程综合，并非 AWS 提供的 Agent 账本实现。

## 根任务拥有预算，子任务只获得受限份额

教学设计为一个可信根任务保留预算 ID、限制版本、已用量、在途预留、总期限和状态。子任务关联相同根任务，获得用途受限的份额；新交接 ID、attempt_id 或[运行时](../../glossary/runtime.md#runtime.virtual-machine)对象都不重置额度。

对调用次数、Token 或金额等累计消耗型额度，一种教学[不变量](../../glossary/systems.md#systems.atomicity)是：

```text
可接纳额度 = 总额度 - 已结算消耗 - 尚未结算的预留
```

“额度”必须使用同一种单位，不能把次数、Token 和金额相加。父任务把 3 次调用额度分给子任务时，这 3 次要么仍在同一账本受控使用，要么在父账本中预留；不能父子两边都继续花同一份余额。归还份额也必须在子任务确实不再有对应在途支出后处理。

可复用的并发槽位另算当前占用，完成并可靠释放后可以再次使用，不把历史已完成次数永久扣在并发上限里；它不能直接套用上面的累计消耗公式。

教学算例：总调用次数额度 12，已结算 4，预留 3，可接纳 5。两个工作者同时各申请 3 次，不能都靠读到余额 5 获准；在没有中间结算或释放的这轮竞争中，权威准入需要原子地检查并更新预算，最多一个可成功，另一个重新判断或停止。这里是纸面不变量，没有实际并发账本实验。

## 预留、派送与结算分别记录

调用前可以在本地事务中记录一次准入预留及待执行意图，关联稳定业务动作与独立尝试标识。重复处理同一准入请求不能重复扣减，真正的新尝试则按规则计数；外部执行不因此加入本地事务。

| 观察到的状态 | 预算处理的教学规则 |
| --- | --- |
| 已预留但确认未派送 | 按契约释放预留，保留准入记录 |
| 已派送且有可信用量 | 按可核实用量结算，去重处理回执 |
| 调用失败但已产生用量 | 仍按真实消耗结算，不能一律退还 |
| 派送或结果未知 | 保留未决预留，查询、对账或按明确政策处理 |

明确政策可以约定保守结算与人工对账条件，但不能仅因等待超时就清零预留，再继续声称费用有硬上限。

“未派送”的确认还需排除旧工作者稍后继续派送；仅看到本地状态没更新不够。释放并发名额也类似：客户端停止等待，不代表远端工作结束。无法可靠观测的在途量，只能说明应用可约束的范围，不能声称全系统并发有硬上限。

费用预留若只是估计值，实际消耗可能超出预留。严格费用上限需要服务端也能约束的最大用量、计价规则和拒绝机制；预估加事后结算只能提供相应策略下的控制，不能凭一个余额字段承诺绝不超支。

## 恢复不重置账本，时钟也要有语义

恢复入口读取当前权威账本与未决预留，不能从旧 [checkpoint](../../glossary/ai.md#ai.state) 覆盖成较早余额。若预算状态和流程状态分属不同存储，需要明确协调、重复恢复与失联时的策略，不能默认一次“保存进度”就把两者原子提交。

[Python time.monotonic](https://docs.python.org/3.13/library/time.html#time.monotonic)适合通过两次读数之差度量本机经过时间，其原点未定义。不能把保存的裸读数当作可跨机器、跨系统重启恢复的通用期限。教学设计可以使用持久化的总到期时间及可信时间策略，恢复时重新计算剩余量，再建立本[进程](../../glossary/systems.md#systems.execution-units)的单调时钟约束；时钟回拨、偏差与等待是否算时需要单独约定。

本文把排队、退避和人工等待计入根任务总期限；如果业务允许暂停期限，必须显式记录暂停和恢复规则。新调用的时限不能超出当前允许的剩余量，还要给保存状态和清理预留空间。

[gRPC Deadlines](https://grpc.io/docs/guides/deadlines/)说明其截止时间传播及取消行为，同时指出服务端应用需要停止自己启动的工作。这是该协议的具体机制；通用工作流不能据此推断所有工具都支持取消，更不能把超时当作远程写入已撤销。

## 收敛规则要覆盖无进展和结果未知

| 情形 | 下一步应由什么决定 |
| --- | --- |
| 可恢复的临时故障 | 安全重放依据、退避、尝试及剩余期限 |
| 输入或权限不满足 | 澄清、重新[授权](../../glossary/security.md#security.identity)或停止，重复相同请求不会自动修复 |
| 角色往返且没有新证据 | 无进展检测、交接上限、澄清或人工处理 |
| 外部效果未知 | 查询或对账能力，不能用剩余预算证明可重复写入 |
| 正常预算耗尽 | 停止新工作，保存部分结果及未决动作，明确收尾责任 |

反复生成同一计划可以消耗步骤却没有业务进展；检测可比较目标、待办与新增证据，而不是只看输出文字是否变化。任何循环还需受到可信计数和期限约束，模型自述“还需要一步”不能提高限额。

停止新动作与清理、查询、对账是不同能力。可提前预留一个用途窄、次数和期限受限的收尾预算，但仍要检查当前权限；不能为“恢复”开放无限免费调用。人工接管需要持久化未决状态、责任人或待办入口与升级规则，不能仅打印一句“请人工处理”就声称责任已移交。

预算耗尽后，流程可以停止调度，已派送动作仍保持 pending 或 unknown。最终输出应分别表达已核实结果、部分完成与未决风险；不要为了得到一个终态而把所有未知动作改成失败或成功。

## 自检与证据边界

自检：总额度剩 5，两个子任务各申请 3，需要什么原子边界？结果丢失为何不能直接退回全部预留？回到旧 checkpoint 为什么不增加额度？期限已到但工具还可能提交时，应该保存哪些未决信息？
